# Сканер вилок

Веб-приложение для автоматического поиска вилок только по реальным данным БК. По умолчанию опрашиваются шесть: **Winline, BetBoom, Fonbet, LeonBet, Betcity, Melbet**; ещё две включаются настройкой — **Liga Stavok** (нужен резидентный прокси, см. `LIGASTAVOK_PROXY`) и **bc.game** (`BCGAME_ENABLED=1`). Демо-режима нет — сканер работает исключительно с настоящей линией.

Сканер работает **только с прематчем**, плюс отдельный опциональный лайв-цикл (см. `LIVE_ENABLED`). Проверяются все события, включая дочерние росписи (тайму, сеты, периоды), и два типа рынков:

- **Любые двухисходные рынки** (движок `find_arbs`):
  - **Победитель без ничьей** — П1 / П2 (напр. теннис, баскетбол, MMA);
  - **Тоталы больше/меньше** — голов, очков, геймов, сетов, а также углов, жёлтых карт, фолов, эйсов, ударов и прочей статистики;
  - **Форы** (гандикапы) — Ф1 / Ф2 с любой линией;
  - **Обе забьют** — Да / Нет (Winline, Fonbet, BetBoom, LeonBet);
  - **Индивидуальные тоталы** — тотал ОДНОЙ команды (ИТБ/ИТМ), вся лестница линий обеих команд, включая таймы/периоды/сеты (Winline, Fonbet, BetBoom, LeonBet). Исход привязан к имени команды, поэтому рынок сшивается даже при перевёрнутом порядке команд у другой БК;
  - **Чет/Нечет** — чётность тотала матча, таймов и периодов (Winline, BetBoom, LeonBet).
- **Трёхисходный рынок «Исход 1X2»** (П1 / X / П2 — победа первой команды, ничья, победа второй; движок `find_arbs_1x2`, вкладки «Вилки 1X2» / «Лайв 1X2»): самый частый рынок футбола и хоккея. Раньше он **отбрасывался целиком** (поддерживались только рынки без ничьей), из-за чего терялась заметная доля вилок именно в футболе — теперь считается по формуле `1/К1 + 1/Х + 1/К2 < 1` с тем же перебором всех комбинаций пар/троек БК. Коэффициент на ничью у каждой БК проходит эвристическую проверку суммарной маржи (`sane_1x2_margin` в `app/parsers/html_utils.py`), чтобы отсеять возможные ошибки разбора фида до попадания в движок поиска вилок.

В теннисе (и других сет-видах: настольный теннис, волейбол, бадминтон) рынки **по геймам** и **по сетам** считаются раздельно: «Тотал 22.5» (геймы) и «Тотал 2.5 (сеты)» — это разные рынки, они не сшиваются между собой. Сет-тоталы и сет-форы (Winline ↔ Fonbet ↔ BetBoom) подписаны «(сеты)», чтобы их нельзя было спутать с рынком по геймам. Пары сет-фор Fonbet ориентированы по-разному (2424 — линия первого игрока, 2421 — второго) — это сверено с ориентированным рынком BetBoom на живых матчах, иначе появлялись бы ложные вилки на 10-20 %.

В киберспорте раздельно считаются **убийства чемпионов** и **объекты карты** — дракон, барон, Рошан, башни, ингибиторы, казармы. Winline подписывает объекты тем же словом («тотал убийств драконов», «фора убийств барона»), поэтому по одному слову «убийства» рынки разъезжались бы в вилку: «фора убийств» BetBoom против «форы убийств дракона» Winline — это ставка на два разных события. Отдельно держатся и «элементальные драконы» (считаются без Элдера), и рынки, которые открываются не с начала карты («фора убийств с 10 минут»).

Каждый рынок сравнивается только с **точно таким же** рынком у других БК: тот же тип, тот же предмет (голы ≠ угловые ≠ карты), та же линия и та же часть матча (тайм/сет/период). Форы дополнительно сшиваются по команде и знаку линии — Ф1(−1.5) одной БК с Ф2(+1.5) другой, а рынки с разным фаворитом не смешиваются. Так исключаются ложные вилки. Счётчик проверенных событий и котировок виден прямо на сайте.

## Как это работает

1. **Каждая БК обновляется в своём потоке и не ждёт остальных.** Обход БК занимает от 2 с (Winline) до ~100 с (BetBoom — полный websocket-фид линии), поэтому общий круг был бы бессмысленным: раньше цикл ждал самую медленную БК, и в шапке висело «Fonbet: 7 минут назад» при собственном обходе в 10 с. Теперь БК обновляется не чаще раза в `SCAN_INTERVAL` (по умолчанию 30 с) и сразу после того, как закончила предыдущий обход, если он длился дольше. В шапке у каждой БК видно возраст её котировок, а пока БК качает линию — ещё и пометка «обновляется…» (обход длится десятки секунд, и без пометки непонятно, БК зависла или как раз работает).
2. Котировки каждой БК **живут между обходами**: если очередной обход БК сорвался, её матчи не пропадают (хранятся до `ODDS_TTL`, по умолчанию 30 минут). Матч, который уже начался, убирается из списка автоматически по времени старта. Если БК отвечает пусто несколько раз подряд, сканер **отступает** — удваивает паузу перед следующей попыткой (до `BK_FAIL_BACKOFF_MAX`): прежний темп запросов ничего не даст, а защита БК от него только злее. Отдельным БК можно задать собственный минимальный период обхода (`BaseParser.min_refresh`; для Betcity — `BETCITY_MIN_REFRESH`, по умолчанию 120 с: снимок всей её линии весит 5–7 МБ, и на частых запросах её сервер рвёт соединение).
3. Вилки считает **один отдельный поток** на сканер. Полный пересчёт по всем БК — это сотни тысяч котировок и секунды работы, а котировки приходят чаще, чем он успевает: обновления, пришедшие во время пересчёта, схлопываются в один следующий проход (иначе за пересчёт платила бы каждая БК и обходы растягивались бы в разы). Между проходами — передышка `ARB_RECALC_MIN_GAP`, чтобы пересчёт не отбирал процессор у самих обходов. Самая дорогая часть пересчёта — фаззи-слияние написаний имён команд (`build_name_canon_map`, 13 с на 300 тыс. котировок): её результат считается раз в `FUZZY_NAME_MAP_REFRESH` и переиспользуется всем — и вилками, и вкладкой «Матчи», и росписью матча. Разбор линии по событиям (что нужно «Матчам») тоже кэшируется, на `MATCHES_CACHE_TTL`: без этого каждый опрос интерфейса пересчитывал бы его заново, и вкладка «Матчи» отвечала по 20 с, отбирая процессор у обходов БК.
4. Для каждого рынка перебираются **все комбинации пар БК**: кэф исхода 1 у одной БК × кэф исхода 2 у другой.
5. Выводится **каждая** комбинация с `1/К1 + 1/К2 < 1` — не только пара с максимальными кэфами. Если тот же рынок даёт вилку и через BetBoom (кэф 1.7), и через bc.game (кэф 1.6), в таблице будут обе строки.
6. Для найденных вилок считается доходность в % и суммы ставок при банке 1 000 / 5 000 / 10 000 ₽ (выигрыш одинаковый при любом исходе).

Пример (тотал убийств в Dota): `ТБ 2.5 = 2.30 (BetBoom)`, `ТМ 2.5 = 1.85 (Winline)` → `1/2.30 + 1/1.85 = 0.9753` → доходность **2.53 %**, при банке 1 000 ₽ ставки **446 ₽ (на ТБ) / 554 ₽ (на ТМ)**.

> **Важно.** Сайты БК доступны только с **российских IP** и защищаются от парсинга. Запускать сканер нужно с машины/VPS с российским IP, иначе котировок не будет (счётчик покажет 0 событий). Fonbet, LeonBet, Betcity и Melbet работают через стабильные JSON-API, Winline и BetBoom — через прямые websocket-фиды линии (без браузера). У Melbet проверка на адрес самая жёсткая, но зависит от зеркала: `melbet.ru` отвечает страницей «отключите VPN» (HTTP 403) всему, что не похоже на домашний российский IP, — включая адреса дата-центров, то есть и ваш VPS, — зато международные зеркала (`melbet.com`, `melbet.org`, `mel-bet.com`) отдают ту же линию и с датацентрового адреса. Поэтому парсер перебирает несколько доменов (`MELBET_HOSTS`); что ответило каждое из них именно с вашего сервера, показывает `venv/bin/python -m app.diagnose_melbet`. Лига Ставок закрыта анти-ботом **Qrator**: он пропускает только «жилые» российские IP, с IP дата-центров (даже российских хостингов) JS-челлендж отклоняется и БК отдаёт 0 котировок — это ограничение самого сайта, а не парсера.

## Возможности

- Таблица вилок: время начала, спорт, матч, рынок (Победитель / Тотал X.X), исходы с их макс. кэфами и БК, доходность %, суммы ставок и прибыль для выбранного банка.
- **Кнопка «Поставить»** у каждой вилки открывает окно быстрой ставки: вводите общую сумму — сканер считает, сколько поставить на каждое плечо и какая будет прибыль, а кнопка «Открыть обе БК» открывает **страницы именно этого матча** на сайтах обеих БК в новых вкладках (суммы копируются в буфер одним кликом). Останется кликнуть нужный кэф и вставить сумму в купон. Поставили — кнопка **«💾 Сохранить ставку»** в том же окне кладёт вилку в личный журнал игрока и поднимает его баланс на её прибыль (см. [«Профиль игрока»](#профиль-игрока-стартовый-баланс-и-журнал-ставок)). Ссылки на матч собираются для Winline (`winline.ru/{stavki|live}/sport/<вид>/<страна>/<чемпионат>/<id>`), Melbet (`melbet.ru/ru/{line|live}/<вид>/<id чемпионата>-<чемпионат>/<CI>-<команды>`), Fonbet (`fon.bet/sports/<вид>/<лига>/<id>`) и BetBoom (`betboom.ru/sport/<вид>/<категория>/<турнир>/<id>`). Полностью автоматическое размещение ставок не делается: для него нужны логины/пароли от аккаунтов БК, а автоматику и вилочников БК активно банят с конфискацией средств.
- На странице котировок матча каждый кэф — ссылка на страницу этого события у соответствующей БК.
- Вкладки «Матчи» и «Лайв-матчи» — **все найденные события всех видов спорта** (футбол, теннис, киберспорт и т.д.) с датами, сгруппированные по матчу. Клик по матчу открывает страницу **всех его котировок**: П1/П2, тоталы и форы по всем линиям, роспись по таймам/периодам/картам, ЖК, угловые и т.д. — кэфы всех БК бок о бок.
- Букмекеры раскрашены фирменными цветами: **Fonbet — красный, BetBoom — синий, Winline — оранжевый**, Лига Ставок — зелёный, bc.game — фиолетовый, LeonBet — жёлтый, Betcity — голубой, Melbet — розовый.
- **Сортировка по любому столбцу** (клик по заголовку), поиск по командам/турнирам, фильтры по виду спорта и БК, фильтр по минимальной доходности. Настройки запоминаются в браузере.
- **Фильтр по букмекеру работает во всех вкладках** (вилки, 1X2, лайв, матчи) — оставляет только строки, где выбранная БК участвует хотя бы одним плечом. Список БК в фильтре берётся из статуса сканера, поэтому выбранная БК не сбрасывается, даже когда под текущие фильтры ничего не попало. Сортировать можно и **по букмекеру**: в таблицах вилок у каждого исхода есть отдельный переключатель сортировки по БК этого плеча (`К1 ▸ БК`), а во вкладках «Матчи» сортируется столбец «Букмекеры».
- Матчи не «слетают» при новом обходе: котировки живут между обходами, начавшиеся матчи убираются автоматически.
- **Переключатель лайва в админке.** Лайв-сканер делит с прематчем процессор и сеть, а его БК обновляются каждые полторы секунды — на слабом VPS это заметно тормозит прематч. В админке (раздел «Сканер») лайв выключается и включается **на ходу**, без перезапуска сервера: воркеры лайв-БК гасятся, как только докачают начатые обходы, а его котировки забываются (показывать кэфы режима, который больше не обновляется, нельзя). Выключение сохраняется в базе и переживает перезапуск. На живой линии выключение лайва подняло сбор BetBoom с ~9 000 до ~50 000 котировок: полный websocket-фид линии успевает прийти целиком за отведённые ему 90 секунд.
- Звуковое уведомление при появлении новой вилки с доходностью > 2.5 % (порог настраивается).
- История всех найденных вилок в SQLite (`GET /api/history`, `GET /api/history_1x2`).
- Защита от блокировок: ротация User-Agent, случайные задержки 2–5 секунд между запросами к одной БК, падение одной БК не останавливает сканер.
- **Выключение и перезапуск отдельной БК из админки** (раздел «Парсеры БК»): у каждой БК свои беды — Betcity рвёт соединение при частых запросах всей линии, у зарубежной bc.game расходятся написания имён команд, а иногда БК отвечает, но линию отдавать перестала. Мешающая БК гасится одной галочкой (её котировки убираются из вилок, решение переживает перезапуск), зависшая — перезапускается с чистой сессией. Там же на карточке БК видно, **почему** она на нуле («ни одно зеркало не отдало линию: melbet.ru → HTTP 403, страница „отключите VPN“»): раньше ноль выглядел одинаково и когда БК просто не успела обновиться, и когда сайт неделю не пускает сервер, а причина лежала только в логах. Раньше и то и другое требовало правки переменных окружения и рестарта сервера. Подробности — в разделе [«Парсеры БК: выключение и перезапуск»](#парсеры-бк-выключение-и-перезапуск).
- **Видно, кто сидит на сайте, и посетителя можно выгнать** (раздел админки «Кто на сайте»): устройство (браузер, ОС, телефон/компьютер), его адреса, кто онлайн прямо сейчас и сколько запросов сделал. Кнопка «Забанить» закрывает сайт для устройства, а не для адреса: у телефона IP меняется каждый день, а метка устройства живёт в cookie — и переживает даже её чистку, если браузер и адрес те же. Подробности — в разделе [«Кто на сайте: устройства посетителей и бан по устройству»](#кто-на-сайте-устройства-посетителей-и-бан-по-устройству).
- **Вход на сайт — по логину и паролю, у каждого свой** (раздел админки «Игроки»): на VPS с публичным адресом вилки и всю линию видел любой, кто знает IP, а один общий пароль на всех не отвечал на вопрос, кто именно смотрит. Учётку заводит только администратор и передаёт реквизиты человеку — самостоятельной регистрации нет. Пароли хранятся в базе только хэшем, забытый сбрасывается кнопкой в админке, а выключенная учётка теряет доступ немедленно, не теряя своего журнала ставок. Подробности — в разделе [«Игроки: учётные записи для входа»](#игроки-учётные-записи-для-входа).
- **Профиль игрока: свой стартовый баланс и журнал прибыли** (`/profile`). Игрок пишет, с какой суммы начал, а дальше нажимает «Сохранить ставку» на каждой вилке, которую поставил руками: вилка со всеми плечами, кэфами и суммами ложится в его журнал, а баланс растёт на гарантированную прибыль. Баланс нигде не хранится отдельным числом — он всегда «стартовый + прибыль журнала», поэтому удаление ошибочной записи пересчитывает его само. Подробности — в разделе [«Профиль игрока»](#профиль-игрока-стартовый-баланс-и-журнал-ставок).
- **Ограничения по IP** остались поверх входа (раздел админки «Доступ к сайту»): строгий режим пускает только адреса из белого списка, чёрный список не пускает никогда. Логин при этом спрашивается всё равно. Подробности — в разделе [«Доступ к сайту: ограничения по IP и запасной пароль»](#доступ-к-сайту-ограничения-по-ip-и-запасной-пароль).
- **Интерфейс:** тёмная и светлая темы (переключатель в шапке, выбор запоминается), сводка состояния в шапке — возраст котировок каждой БК с индикатором и пометкой у выключенной; на телефоне таблицы разворачиваются в карточки с подписями столбцов, а поиск и фильтры свёрнуты в одну кнопку, чтобы первый экран занимали сами вилки. В росписи матча у каждого кэфа подписана его БК, а лучший кэф исхода помечен «▲» — по одному цвету рамки БК не различить, особенно на телефоне, где подсказки по наведению нет.
- **Админка** (`/admin`, логин/пароль `admin` / `admin1` по умолчанию — **смените на проде**): учётные записи игроков, подключение аккаунтов БК, чтение баланса, лимит ставки на каждую вилку (`max_stake`), управление парсерами и защита сайта. Подробности — в разделе [«Админка, аккаунты БК и авто-ставки»](#админка-аккаунты-бк-и-авто-ставки).
- **Авто-ставка временно спрятана из интерфейса** (`AUTOBET_UI=0`, по умолчанию): кнопки в карточке вилки и разделов «Авто-ставки» и «Журнал ставок» в админке нет. Сам механизм цел — ручка `POST /api/autobet/place`, коннекторы, расчёт сумм и журнал остались на месте, и `AUTOBET_UI=1` возвращает интерфейс как был. Ставки сейчас делаются руками, а кнопка «поставить за меня» рядом с реальными деньгами — лишний повод нажать не туда.

## Быстрый запуск на своём компьютере

Нужен Python 3.10 или новее.

```bash
git clone https://github.com/filippin4ik-dev/bet.git
cd bet
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Открыть в браузере: http://localhost:8000

Сканер сразу начинает парсить реальную линию БК. С не-российского IP котировок не будет (в шапке будет «Проверено: 0 событий») — это ограничение самих БК, а не приложения.

### Шаг 3. Диагностика: проверить, что БК вообще отдают данные

Перед запуском сайта прогоните диагностику — она покажет ваш IP и страну, доступность Selenium и сколько котировок реально отдаёт каждая БК:

```bash

```

Что означают результаты:

- **страна не RU** — сайты БК почти наверняка вернут 0. Нужен VPS с российским IP.
- **Selenium недоступен** — Лига Ставок вернёт 0 (это SPA, без браузера её не спарсить). Проверьте, что установлены `chromium-browser` и пакет `selenium`. Winline и BetBoom браузер не используют — если они отдают 0, проверьте `pip install websocket-client` и доступность фидов линии (`wss://wss.winline.ru`, `wss://ru-ws2.sporthub.bet`).

### Шаг 9 (важно). Завести учётные записи

Сайт закрыт всегда: без входа посетитель не видит ни вилок, ни линии. Сразу после запуска учёток игроков ещё нет, и войти можно только реквизитами администратора (`ADMIN_USERNAME` / `ADMIN_PASSWORD`, по умолчанию `admin` / `admin1` — **смените их на проде**); при старте об этом пишется предупреждение в лог.

Зайдите на `/login` под администратором, оттуда в `/admin` → раздел **«Игроки»** и заведите учётку каждому, кто будет пользоваться сканером: логин, пароль и (по желанию) стартовый баланс. Пароль после сохранения не показать никому, включая вас, — в базе лежит только хэш, поэтому передайте реквизиты человеку сразу. Подробности — в разделе [«Игроки: учётные записи для входа»](#игроки-учётные-записи-для-входа).

Дополнительно можно ограничить доступ по адресу (строгий режим белого списка) в разделе **«Доступ к сайту»** — подводные камни (обратный прокси, защита от самоблокировки) описаны в разделе [«Доступ к сайту: ограничения по IP и запасной пароль»](#доступ-к-сайту-ограничения-по-ip-и-запасной-пароль).

Если сайт стоит за nginx из `deploy/nginx.conf`, определение IP клиента уже настроено: nginx передаёт `X-Forwarded-For`, а приложение доверяет этому заголовку только когда запрос пришёл из локальной сети, то есть от самого nginx.

### Обновление до свежей версии

```bash
cd /opt/arb-scanner
git pull
venv/bin/pip install -r requirements.txt
systemctl restart arb-scanner
```

Отдельная миграция базы не нужна: новые таблицы (`players`, `player_bets`) создаются при старте через `CREATE TABLE IF NOT EXISTS`, старые данные остаются на месте. Но после обновления **сайт закрыт входом по логину и паролю**, а учёток игроков в базе ещё нет — первым делом войдите реквизитами администратора и заведите их в разделе «Игроки» (см. [шаг 9](#шаг-9-важно-завести-учётные-записи)).

**Если после обновления сайт выглядит по-старому** (нет обещанного раздела в админке, интерфейс не поменялся) — проверьте по порядку, на каком шаге версия «застряла»:

```bash
cd /opt/arb-scanner
git status                      # на какой ветке сервер и нет ли локальных правок, из-за которых pull не прошёл
git log --oneline -3            # верхний коммит должен совпадать с верхним коммитом ветки на GitHub
systemctl status arb-scanner    # процесс должен быть перезапущен ПОСЛЕ pull, иначе в памяти старый код
```

Частые причины, по которым `git pull` не приносит ожидаемого:

- **Сервер сидит на своей ветке, а работа влита в другую.** `git pull` обновляет только текущую ветку: если на VPS `main`, а нужный код слит в фича-ветку (или наоборот), локально ничего нового не появится, хотя на GitHub всё есть. Лечится `git checkout main && git pull` — держать прод на `main` и вливать всё туда.
- **Процесс не перезапущен.** Python держит код в памяти: до `systemctl restart arb-scanner` (или кнопки «Перезапустить сервер» в админке) правки в `app/` не действуют. HTML/CSS/JS из `static/` при этом подхватываются сразу — поэтому «интерфейс новый, а поведение старое» бывает, а обратное почти всегда значит, что pull не прошёл.
- **Кэш браузера.** Статика отдаётся с `Cache-Control: no-cache`, так что обычного F5 достаточно; если страница всё же старая — жёсткая перезагрузка (Ctrl+Shift+R) или проверка `curl -s localhost:8000/static/app.js | head` прямо на сервере покажет, что лежит на диске.

## Настройки (переменные окружения)

| `SCAN_INTERVAL` | `30` | Как часто обновлять котировки ОДНОЙ БК, сек. Каждая БК крутится в своём потоке, поэтому это период обхода конкретной БК, а не общего круга. Больше значение — реже запросы и меньше трафика, но кэфы старше (см. [«Сколько это ест ресурсов»](#сколько-это-ест-ресурсов)) |

### Сколько это ест ресурсов

Замеры на живой линии из пяти БК (Winline, BetBoom, Fonbet, LeonBet, Betcity — около 300 000 котировок в памяти), лайв выключен, дефолтные настройки:

| Что | При `SCAN_INTERVAL=30` | При `SCAN_INTERVAL=90` |
|---|---|---|
| Трафик | ~3–5 ГБ в час | ~3 ГБ в час |
| CPU | ~90 % одного ядра | ~65 % одного ядра |
| Свежесть котировок | 30 с (Winline, Fonbet) … 100 с (BetBoom), Betcity — 120 с | 45–120 с |

Основной трафик дают тяжёлые БК (полная роспись LeonBet и Betcity, websocket-фид BetBoom), а их обход и так длится дольше `SCAN_INTERVAL` — поэтому переменная сильнее всего влияет на быстрые Winline и Fonbet. Если у VPS лимит по трафику, поднимайте `SCAN_INTERVAL`; если тесно по процессору — `ARB_RECALC_MIN_GAP`. Ещё дешевле обходится отключение полной росписи (`LEON_FULL_MARKETS=0`, `BETCITY_FULL_MARKETS=0`, `BETBOOM_FULL_MARKETS=0`, `MELBET_FULL_MARKETS=0`), но тогда останутся только топ-рынки и вилок будет заметно меньше. Включённый лайв добавляет к этому свою постоянную нагрузку — его можно выключить в админке.

**Память:** на полной росписи пяти БК процесс занимает **2–2.5 ГБ** — это сами котировки плюс промежуточные структуры пересчёта вилок. Берите VPS минимум с 4 ГБ (2 ГБ хватит только с отключённой полной росписью).

## Диагностика («почему 0 котировок»)

Запустите `venv/bin/python -m app.diagnose` — покажет IP/страну, доступность Selenium и что отдаёт каждая БК. Отдельно по Melbet есть `venv/bin/python -m app.diagnose_melbet`: её фид отвечает только российским адресам и не подписывает рынки словами, поэтому скрипт показывает, какое зеркало ответило, какие пары «группа + код исхода» приехали и как разложилась разметка (см. раздел [«Важно про парсинг»](#важно-про-парсинг)). Если линии нет вовсе, `venv/bin/python -m app.diagnose_melbet --api` разбирается почему: печатает ответ каждой площадки вашему серверу (код, переадресацию, заголовок страницы, признаки анти-бота) и ищет настоящий адрес фида в скриптах сайта.

> Все скрипты запускаются **интерпретатором из venv и из каталога проекта** (`cd /opt/arb-scanner`). Системный `python -m app.diagnose_melbet` падает с `ModuleNotFoundError: No module named 'bs4'` — зависимости стоят в `venv`, а не в системе; это не поломка сканера.

Частые причины пустого результата:

1. **IP не российский.** Сайты БК доступны только из РФ. Решение — VPS с российским IP. Для Лиги Ставок этого мало: её анти-бот Qrator отклоняет IP **дата-центров** (в т.ч. российских хостингов, проверено на московском VPS — 403-заглушка «доступ ограничен») — нужен «жилой» (резидентный) IP или прокси. Поэтому **по умолчанию Лига Ставок выключена** и включается автоматически, когда задан резидентный прокси `LIGASTAVOK_PROXY` (см. таблицу настроек); для прохождения браузерного челленджа включите у провайдера прокси **авторизацию по IP** вашего сервера. На «жилом» IP без прокси включайте вручную: `LIGASTAVOK_ENABLED=1`. Остальные шесть БК работают без этого.
2. **Не установлен Selenium/Chromium или Chromium из snap не стартует.** Лига Ставок — это SPA, её линия грузится JavaScript'ом, поэтому нужен браузер. Fonbet, Winline и BetBoom работают без браузера (Fonbet — JSON-API, Winline и BetBoom — прямые websocket-фиды линии; нужен `pip install websocket-client`).

   ⚠️ **Chromium из snap (пакет `chromium-browser` на Ubuntu ставится как snap) под systemd часто не запускается** — в логе `Service /snap/bin/chromium.chromedriver unexpectedly exited. Status code was: 1`, и Лига Ставок даёт 0. Скачанный драйвер тоже не может управлять snap-хромом (конфайнмент). Решение — поставить **не-snap** Google Chrome и указать его сканеру:

```bash
cd /tmp
wget -q https://dl.google.com/linux/direct/google-chrome-stable_current_amd64.deb
apt install -y ./google-chrome-stable_current_amd64.deb
snap remove chromium 2>/dev/null; apt-get remove -y chromium-browser 2>/dev/null; true
# указать бинарь в юните (драйвер сканер подберёт сам через Selenium Manager)
echo 'Environment=CHROME_BINARY=/usr/bin/google-chrome' >> /etc/systemd/system/arb-scanner.service
systemctl daemon-reload && systemctl restart arb-scanner
```

   Сканер сам предпочитает не-snap браузер и при сбое явного драйвера откатывается на авто-подбор (Selenium Manager), но исправный не-snap Chrome для этого должен быть установлен.
3. **Сменился домен линии Fonbet.** Домены вида `lineNNw.<hash>.com` периодически меняются. Парсер перебирает известные кандидаты (включая формат `line01w.bk6bba-resources.com`), но если все не подошли — найдите актуальный хост в браузере (DevTools → Network → запрос `events/list`/`events/listBase`) и задайте `FONBET_LINE_HOST`.
4. **Изменилась вёрстка Лиги Ставок или схема фидов Winline/BetBoom.** CSS-селекторы Лиги Ставок в `app/parsers/ligastavok.py` могут потребовать актуализации под текущую разметку; для Winline — номера шагов/полей бинарного фида в `app/parsers/wl_feed.py`, для BetBoom — номера полей protobuf в `app/parsers/bb_feed.py`. Структура парсеров при этом сохраняется.
5. **Слабый VPS: не хватает памяти.** Chrome + сканер требуют ~1.5–2 ГБ. Если в логе процесс внезапно завершается словом `Killed` — это OOM-killer. Добавьте swap (после этого перезапустите сканер):

```bash
fallocate -l 2G /swapfile && chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab   # чтобы пережил перезагрузку
```

6. **Betcity рвёт соединение на всех запросах** (`Connection reset by peer` в логе, причём и на снимок линии, и на обычный `https://betcity.ru/`, тогда как остальные БК отвечают нормально) — её защита наказала IP за слишком частые запросы всей линии. Такое ловится при отладке, когда сканер запускают несколько раз подряд или держат два инстанса на одном IP. Лечится ожиданием (блокировка временная) и увеличением `BETCITY_MIN_REFRESH`; сканер тем временем сам отступает (`BK_FAIL_BACKOFF_MAX`) и держит прежние котировки Betcity до `ODDS_TTL`.

Рекомендуемый минимум для VPS: **2 vCPU и 4 ГБ RAM** (+2 ГБ swap) при полной росписи всех БК — на живой линии процесс занимает 2–2.5 ГБ (см. [«Сколько это ест ресурсов»](#сколько-это-ест-ресурсов)). На 2 ГБ RAM отключайте полную роспись (`LEON_FULL_MARKETS=0`, `BETCITY_FULL_MARKETS=0`, `BETBOOM_FULL_MARKETS=0`) или держите swap.

### Почему мало вилок прематч (котировки при этом есть)

Если `venv/bin/python -m app.diagnose` показывает десятки тысяч котировок у каждой БК, а вилок находится единицы — это почти всегда **не ошибка сопоставления**, а следствие нескольких факторов (проверено на живых данных всех БК):

1. **Лига Ставок отключена без резидентного прокси** (см. пункт 1 выше) — вместо 5 БК в сопоставлении фактически участвуют 4, меньше пар — меньше шанс на вилку.
2. **Реальная эффективность рынка.** У событий, которые видят ≥2 БК одновременно, собственная маржа букмекера на пересекающемся рынке (1/К1+1/К2+…) обычно 5–9 % — этого края обычно не хватает, чтобы кэфы разных БК разошлись в вилку; вилки 15-25%+ почти всегда ошибка сопоставления и отбрасываются (`ARB_MAX_PROFIT`), а не реальная возможность.
3. **Bc.game отдаёт часть команд/игроков на английском**, если для них нет русской локализации (индивидуальные виды спорта — теннис/бокс в формате «Фамилия, Имя», малоизвестные клубы) — такие имена не совпадут с кириллическими у остальных БК ни при какой нормализации. Это ограничение исходных данных площадки, а не парсера.
4. **(Исправлено)** Экзотические рынки Winline (src=16 — их у Winline сотни: тоталы/форы/чет-нечет по угловым, карточкам, ударам, офсайдам, 2-му тайму и т.п.) раньше распознавались по жёсткому белому списку конкретных текстов и терялись почти полностью (~2 % типов) — Winline тихо не отдавал тоталы угловых/карточек, которые Fonbet и BetBoom отдают, поэтому такие рынки не с чем было сшивать. Теперь `is_decodable_exotic` (`app/parsers/wl_feed.py`) распознаёт их семантически (по слову тотал/фора/чет-нечет + подписям исходов, а не по тексту целиком) — Winline отдаёт в 1.5+ раза больше котировок за счёт этих рынков.
5. **(Исправлено)** **Фора всего матча не сшивалась между БК из-за формы ключа рынка.** Ключ рынка собирает парсер, и на рынке БЕЗ уточнения (то есть на рынке всего матча — самом ходовом) БК разошлись в мелочи: Betcity и LeonBet писали фору как `hcap:-1.5`, а Winline, BetBoom, Fonbet, Melbet, bc.game и Лига Ставок — как `hcap::-1.5`, с пустым сегментом на месте `scope`. Строки разные, значит и группа разная — основная фора матча **никогда** не сопоставлялась между этими двумя наборами БК, и все вилки по ней терялись. Заметить это со стороны было нельзя: обе БК показывали рынок под одинаковой подписью «Фора -1.5» (`display_market` читает обе формы), в списке матчей он был виден у обеих, а в вилки не попадал. Теперь форма ключа приводится к общей в одном месте (`canon_market_key` в `app/parsers/html_utils.py`) — и на входе движка (`_explode`/`_market_group`), и в самих парсерах; там же выравнивается запись линии, чтобы «1.5» и «+1.5» (или «2.0» и «2») не разводили один рынок по разным группам. Там же ключ добивается до разбираемой по сегментам формы, и это не косметика: на ключе неожиданного вида (`hcap` без сегментов, `itotal` без `scope`) разбор падал с `ValueError` — **внутри общего пересчёта**, то есть одна кривая котировка одной БК уносила разом **все** вилки по всем БК, и так каждый цикл, пока она жива (до получаса `ODDS_TTL`). Не понять один рынок можно, потерять всю линию — нет.
6. **(Исправлено)** **Третья БК оставалась без пары при слиянии написаний имён.** Фаззи-слияние (пункт 7 ниже) ради экономии сравнений выбрасывало из поиска написания, которые уже совпали точно у 2+ БК. Логика «им сравнение не нужно» неверна: если две БК пишут «Црвена Звезда» одинаково, а третья — «Црвена Зведза», то общее написание в сравнении не участвовало, третьей БК было не с чем слиться, и её кэфы не попадали в событие вообще. Чем больше БК в наборе, тем чаще срабатывала эта потеря — то есть добавление новой БК могло не добавить вилок, а отнять. Теперь сравниваются все написания, а экономия другая и безопасная: одинаковые написания разных БК схлопываются в одну запись, а перед дорогим `difflib` стоит честный предфильтр по «паспорту» имени (длина + маска символов), который не отсекает ничего, что `difflib` признал бы похожим. На синтетической линии в 180 тыс. котировок слитых имён стало 900 вместо 227 при вчетверо меньшем времени построения карты.
7. **(Исправлено)** **В лайве слияние написаний не работало вовсе.** `build_name_canon_map` брала в работу только прематч, а лайв-сканер держит ТОЛЬКО лайв-котировки — значит карта имён у него всегда выходила пустой, и любое расхождение в написании между БК стоило лайв-вилки целиком. Время старта у лайв-котировки есть (время начала уже идущего матча) и как якорь окна кандидатов работает не хуже прематчевого.
8. **(Исправлено)** **Один и тот же рынок расходился по группам из-за формулировки БК.** Ключ рынка содержит `scope` — канонический «предмет» рынка, который `market_scope` (`app/parsers/html_utils.py`) собирает из подписи БК. В подписи почти всегда есть и уточняющее слово, и общее, а соседняя БК пишет только уточнение — и общее слово добавляло лишний токен: «Угловые удары» давали `corners+shots` против `corners` у «Тотал угловых», «Жёлтые карты» — `cards+maps` против `cards` у «Тотал карточек», «Красные карты» — `maps+redcards` против `cards+redcards` у «Красных карточек». Тотал угловых и тотал ЖК — самые ходовые рынки после основных, и вилки по ним между такими БК не находились вовсе. Теперь уточняющий токен вытесняет общий (`_REFINES` — обобщение прежнего правила «объект карты вытесняет убийства» из киберспорта), а разные слова для одного предмета сведены к одному токену («Нарушения» = «Фолы», «Вбрасывания» = «Вбросы», «Положение вне игры» = «Офсайды», «Подачи навылет» = «Эйсы»).
9. **(Исправлено)** **Основной рынок терялся от одного незнакомого слова.** Незнакомое слово в подписи уходит в ЗАПАСНОЙ токен `scope` — намеренно, чтобы экзотика не сливалась с основным рынком в ложную вилку. Но словарь служебных слов был неполон по падежам и синонимам, и на него попадались самые обычные подписи: «Тотал мячей», «Количество мячей», «Фора по мячам» (мяч = гол), «Тотал по очкам», «Фора по голам», «Итог матча», «Итоговый результат», «Тотал результативности», «Основной исход», «Исход основного времени». Такой рынок переставал быть основным и не сшивался уже **ни с одной** БК — терялся самый ходовой рынок целиком, у той БК, которая так его подписывает. Словарь дополнен; «пропущенные» намеренно оставлены отдельным рынком — индивидуальный тотал пропущенных не равен забитым, слить их значило бы выдать ложную вилку.
10. **(Исправлено)** **Лайв-котировка без времени старта выпадала из слияния имён.** Слияние написаний брало только котировки с распознанным временем старта — оно служит якорем окна кандидатов. Но лайв-парсеры, в отличие от прематчевых, время старта НЕ требуют (матч уже идёт, отбрасывать его не за что), и у BetBoom, Fonbet, Melbet и bc.game оно вполне может не прийти: такая БК выпадала из карты имён целиком, и её кэфы не попадали в событие. В лайве это тем обиднее, что событие по времени там и не разбивается (`_time_clusters` работает только по прематчу) — якоря нет ни у кого, терять было нечего. Теперь лайв-событие без времени сравнивается со всем корнем вида спорта без окна; прематч без времени старта по-прежнему мимо — там окно единственное, что отделяет первый матч пары от ответного.
11. **(Исправлено)** **Запасной разбор страницы брал стороны тотала по порядку в вёрстке.** ТБ и ТМ считались первым и вторым кэфом подряд, а порядок исходов в вёрстке у БК не закреплён. Перепутанные стороны хуже потерянного рынка: ключ у них тот же, и движок сведёт ТБ одной БК с ТБ другой по ЧУЖОЙ цене — покажет вилку, которой нет, и не покажет ту, которая есть. Теперь стороны опознаются по подписи исхода (текстом или атрибутом разметки), а порядок вёрстки берётся, только когда подписи нет вовсе. Касается запасного HTML-разбора Лиги Ставок — он включается, когда не отвечает её API.
12. **(Исправлено)** **После каждого запуска карта имён пять минут была пустой.** Слияние написаний (пункты 6-7, 10 и 13) стоит секунд на живой линии, поэтому карта кэшируется на `FUZZY_NAME_MAP_REFRESH` (5 минут). Но слияние существует только МЕЖДУ РАЗНЫМИ БК, а первый пересчёт вилок запускается, едва отчиталась ПЕРВАЯ БК, — карта по одной БК пуста по построению, и эта пустая карта застревала на пять минут, пока остальные БК давно принесли линию. Всё это время вилки по событиям с разным написанием имени не находились — и так после каждого запуска, каждого перезапуска сканера и каждого включения лайва. Теперь появление БК, которой в карте не было, пересобирает карту сразу, не дожидаясь срока; знакомый набор БК срока по-прежнему не отменяет.
13. **(Исправлено)** Разное написание имени одной и той же команды/игрока у разных БК (транслитерация, опечатки, сокращения: «Кимчхон Санму»/«Кимчхон Сангму», «Виктория Плзень»/«Виктория Пльзень», «ГВС Джайнтс»/«ГВС Джайентс») — раньше событие не склеивалось совсем, если хотя бы одна команда была записана по-разному, хотя `start_ts` совпадал. Диагностика (`app.diagnose_overlap`, раздел «Почти совпадения») на живых данных нашла **тысячи** таких пар. Теперь `build_name_canon_map` (`app/arbitrage.py`) сливает написания с похожестью ≥ `FUZZY_NAME_SIM_THRESHOLD` (0.9 по умолчанию, с полом на похожесть каждой отдельной команды `FUZZY_NAME_MIN_SINGLE_RATIO` — защита от ложного слияния «одна команда совпала, другая нет»); слияние ограничено окном по времени старта и НЕ распространяется на события одной и той же БК. На живых данных доля событий, совпавших у 2+ БК, выросла с ~20 % до ~32 % (футбол — с 26 % до 39 %, теннис — с 13 % до 29 %, настольный теннис — с 19 % до 32 %). Само по себе слияние имён не создаёт вилку — событие всё равно дополнительно проверяется по времени старта (`_time_clusters`), так что риск ложной склейки минимален.

Проверить пересечение событий/рынков между БК на живых данных без запуска всего сканера:

```python
python3 -c "
from app.parsers import get_parsers
from app.arbitrage import find_arbs
odds = [o for p in get_parsers() for o in p.safe_fetch()]
print('котировок:', len(odds))
print('вилок:', len(find_arbs(odds)))
"
```

Если и это не объясняет низкое число вилок (например, событий с 2+ БК заметно меньше, чем ожидалось от объёма котировок), запустите на сервере более подробную диагностику пересечения:

```bash
python3 -m app.diagnose_overlap
```

Скрипт покажет: сколько уникальных событий нашла каждая БК, матрицу пересечений событий по парам БК, **разбивку по видам спорта** (сколько событий у каждого спорта и какая доля из них совпала у 2+ БК, плюс сколько вилок нашлось именно в нём), сколько совпавших событий не имеют ни одного общего рынка (вилка невозможна даже при совпавшем матче), и два отдельных списка несовпавших пар:

- **«Разошлись по времени старта»** — события с ОДИНАКОВЫМИ (после нормализации, без учёта порядка команд) именами у разных БК, которые всё равно не склеились, потому что их `start_ts` отличается больше, чем боевой допуск сканера для этого вида спорта (см. выше `_start_tolerance`). Это НЕ баг нормализации имён — сигнал о неточном времени у одной из БК (типично для зарубежных турниров) или о том, что для конкретного вида спорта стоит точечно расширить допуск.
- **«Почти совпадения»** — пары событий с похожим, но НЕ идентичным после нормализации названием команд и близким временем старта. Пары с похожестью ≥ `FUZZY_NAME_SIM_THRESHOLD` сканер **уже сливает сам** (`build_name_canon_map`, см. раздел «Почему мало вилок прематч» выше) — в этом разделе останутся в основном пары НИЖЕ порога, оставленные на ручной разбор осознанно (риск ложной склейки РАЗНЫХ клубов — например, «Динамо Москва» и «Динамо Минск» — при слепом отбрасывании уточнений слишком высок). Если среди них найдутся явные дубликаты, вручную проверьте на сайтах БК, что это действительно один и тот же матч, и точечно поднимите `FUZZY_NAME_SIM_THRESHOLD`/добавьте алиас под конкретный случай.

Разбивка по спорту особенно полезна для интерпретации результата: если у футбола/хоккея/баскетбола доля совпадения событий ВЫСОКАЯ (события сшиваются нормально), но вилок в них 0 — это ожидаемо (пункт 2 выше, эффективный рынок), а не баг; вилки естественным образом концентрируются в нишевых рынках (тоталы по сетам в волейболе, небольшие турниры киберспорта), где букмекеры расходятся в оценке сильнее. А вот НИЗКАЯ доля совпадения у популярного спорта — уже сигнал, что там что-то не сшивается, и стоит смотреть «почти совпадения» именно для него.

## Важно про парсинг

- Сайты БК доступны **только с российских IP** и активно защищаются от парсинга; вёрстка и домены периодически меняются — это нормально для парсеров БК и иногда требует ручной подстройки.
- Все парсеры отдают двухисходные рынки в едином виде: победитель, тоталы (с предметом — голы/углы/карты/сеты/…), форы (со знаковой линией). Предмет и часть матча приводятся к канону функцией `market_scope` в `app/parsers/html_utils.py`, поэтому один и тот же рынок разных БК сопоставляется независимо от формулировки.
- Парсер **Fonbet** работает через публичный JSON-API линии (без браузера): победитель (921/923), **вся лестница** линий тоталов (930/931, 1696/1697, 1727/1728, 1730/1731, 1733/1734, 1736/1737, 1739/1791, 1793/1794, 1796/1797, 1799/1800, 1802/1803, 1805/1806; тотал очков ракеточных видов 1848/1849), лестница фор (910/912, 927/928, 989/991, 1569/1572, 1672/1675, 1677/1678, 1680/1681, 1683/1684, 1689/1690; фора по очкам 1845/1846), «Обе забьют» (4241/4242), **индивидуальные тоталы обеих команд** (лестницы 1809…1828 — команда 1, 1854…1887 — команда 2; сторона и порядок Больше/Меньше сверены с рынком «Тотал <команда>» BetBoom) и сет-рынки тенниса (тотал сетов 917/918, форы по сетам 2422/2421 и 2424/2425), включая дочерние росписи (тайму/сеты/угловые/карты). Все пары id сверены с теми же рынками Winline/BetBoom на живой линии.
- Парсер **Winline** подключается напрямую к бинарному websocket-фиду сайта (`wss://wss.winline.ru/data_ng`, см. `app/parsers/wl_feed.py`) и забирает **всю** прематч- и лайв-линию без браузера. Снапшот прематча содержит только топ-линии (~10 на матч), поэтому фид дополнительно выкачивает **полную роспись каждого события** командой «event.plus» (как сайт при открытии страницы матча): все линии тоталов и фор, таймы/периоды, «Обе забьют» — в несколько раз больше котировок. Из «экзотики» (src=16, у Winline это сотни разных типов линий) рынки распознаются СЕМАНТИЧЕСКИ (`is_decodable_exotic` в `wl_feed.py`) — по ключевому слову тотал/фора/чет-нечет в тексте типа линии и подписям исходов из справочника (Больше/Меньше, 1/2, Нечет/Чет), а не по жёсткому списку конкретных формулировок: так подхватываются тоталы/форы/чет-нечет **любого предмета и периода** — угловые, карточки, удары, офсайды, штрафные минуты, 2-й тайм, N-й сет/период/карта и т.п., плюс **индивидуальные тоталы** @1/@2 конкретной команды. Раньше жёсткий белый список ловил лишь ~2 % типов линий src=16 (терялись, в частности, популярные для вилок тоталы угловых/карточек — Fonbet и BetBoom их отдают, а Winline вслепую отбрасывал). Частота запросов ограничена (`WINLINE_PLUS_RATE`), роспись обновляется по кругу (`WINLINE_PLUS_REFRESH`). Соединение держится постоянно, дельты применяются на лету. При смене протокола правьте номера шагов/полей в `wl_feed.py`.
- Парсер **BetBoom** подключается напрямую к websocket-фиду линии (sporthub, protobuf) и забирает **всю** прематч-линию (несколько тысяч матчей) без браузера. Дерево турниров отдаёт лишь топ-ставки (~7 на матч), поэтому парсер дополнительно подписывается на **полную роспись каждого матча** (`state_subscribe_matches`): все тоталы/форы по всем линиям, таймы/периоды/карты, ЖК, угловые и т.д. — это даёт ~40 000 котировок вместо ~4 000 (отключается `BETBOOM_FULL_MARKETS=0`). При смене схемы правьте номера полей в `app/parsers/bb_feed.py`.
- **Лига Ставок** закрыта анти-ботом **Qrator** (JS-челлендж с proof-of-work на каждый запрос), поэтому **по умолчанию отключена** — включается автоматически при заданном `LIGASTAVOK_PROXY` (или принудительно `LIGASTAVOK_ENABLED=1`). Парсер сначала пробует **внутренний JSON-API** линии (`lds-api-sites.ligastavok.ru`, `POST /rest/events/v8/eventsList`) — сразу, даже без cookie; если Qrator его блокирует — рендерит страницу браузером (Selenium + Chromium), ждёт прохождения челленджа (`LIGASTAVOK_CHALLENGE_WAIT`), переносит полученные Qrator-cookie в HTTP-сессию и повторяет API; последний рубеж — разбор HTML из отрендеренного DOM. **Qrator пропускает только «жилые» российские IP**: с IP дата-центров (проверено на московском VPS) он отдаёт 403-заглушку «доступ ограничен» даже настоящему Chrome — тогда БК отдаёт 0 котировок (в логе будет явное предупреждение с заголовком полученной страницы). Решение — резидентный прокси в `LIGASTAVOK_PROXY`: HTTP-запросы парсера идут через него целиком, браузер — тоже (но только с авторизацией по IP: логин/пароль прокси Chrome не передаёт). Через «жилой» прокси мобильный API обычно отвечает сразу и браузер вообще не нужен. При смене API/вёрстки правьте `app/parsers/ligastavok.py`.
- Парсер **bc.game** работает через публичный REST-фид спортивной платформы **BetBy** (`cocoesports.com` — российское «зеркало» фида, без авторизации): индекс `/api/v4/prematch/brand/<brand>/ru/0` перечисляет версии чанков, из чанков склеивается полная линия (несколько тысяч событий), а справочник рынков `/api/v3/descriptions/.../markets/ru` даёт русские названия. Разбираются победитель/ставка без ничьей, тоталы, форы (в т.ч. по геймам/сетам), «Обе забьют», чет/нечет и индивидуальные тоталы. `brand_id` bc.game периодически меняется — парсер узнаёт актуальный с сайта, а при неудаче берёт `BCGAME_BRAND_ID`. В отличие от БК РФ, фид bc.game доступен и с зарубежных IP.
- Парсер **LeonBet** работает через публичный JSON-фид линии сайта (без браузера и авторизации, см. `app/parsers/leon.py`): `GET {LEON_API_HOST}/api-2/betline/changes/all` отдаёт снимок всей линии (прематч+лайв) с «топ»-рынками каждого события (~9: исход/1X2, основная фора/тотал, тайм-маркеты, «обе забьют»), а `GET .../api-2/betline/event/all?eventId=<id>` — полную роспись рынков конкретного события (лестница доп. линий тоталов/фор и т.п.), которая забирается **параллельно по всем событиям** (пул потоков, `LEON_FULL_MARKETS_WORKERS`, отключается `LEON_FULL_MARKETS=0`). В отличие от Winline/Fonbet, где рынок надо узнавать по числовому id, у Leon рынки размечены семантически: у каждого рынка `typeTag` (REGULAR/TOTAL/HANDICAP), у исхода — `tags` (HOME/AWAY/DRAW/OVER/UNDER/YES/NO/ODD/EVEN), а у тоталов/фор знак линии несёт сам исход (`runner.handicap`) — это делает разбор устойчивым к смене вёрстки. Разбираются 1X2 (с проверкой маржи `sane_1x2_margin`), победитель без ничьей, форы, тоталы (в т.ч. индивидуальные — «Тотал хозяев/гостей»), «Обе забьют» и чет/нечет основного рынка. Сложные/многоисходные рынки («Двойной исход», «Кто забьёт первый гол» и т.п.) и командные варианты да/нет и чет/нечет (не отличимые от общерыночных по одним `tags`) намеренно пропускаются, чтобы не склеить в вилку разные по смыслу рынки.
- Парсер **Betcity** работает через публичный JSON-API линии (см. `app/parsers/betcity.py`) — БЕЗ браузера и БЕЗ авторизации, хотя сама страница `betcity.ru/ru/line` защищена антифрод-скриптом «gib» (Group-IB): в headless/headed Chrome (в т.ч. со стелс-флагами и Xvfb) страница рендерит DOM, но реальные котировки так и не подгружаются — сайт использует long-polling XHR к `lf.betcity.ru`, инициализация которого в автоматизированном браузере не проходит. Однако САМ REST API линии, который дёргает этот JS (домен `ad.betcity.ru`, вычислен и сверен по маршрутам Angular-роутера из бандла сайта), оказался доступен НАПРЯМУЮ обычным HTTP-запросом — никакого анти-бота на самом API нет: `POST {BETCITY_API_HOST}/d/off/events?rev=6&template=1` (тело `ids=0`) одним запросом отдаёт ВСЮ прематч-линию сайта (все ~33 вида спорта, тысячи событий, несколько МБ). Рынок распознаётся по форме «блока» коэффициентов, а не по числовому id (один и тот же id рынка Betcity переиспользует для разных по смыслу рынков): блок `Wm`/`W` с исходами {П1,X,П2} — «Исход 1X2», {П1,П2} — победитель без ничьей; `F1m`/`F1` — фора (знак линии на стороне исхода); `T1m`/`T` — тотал; `IT_T1`/`IT_T2` — индивидуальные тоталы команд; `YN` — да/нет («Обе забьют») и чет/нечет. Betcity считает статистику матча (угловые, жёлтые карты, офсайды, удары, фолы, вбросы, попытки, подборы, передачи и т.п.) отдельными «Фактический исход/Фора/Тотал»-рынками с текстовым префиксом-предметом («УГЛ. Фора», «ЖК. Тотал») — предмет разворачивается в полное слово («УГЛ.»→«угловые.») перед канонизацией `market_scope()`, иначе не сошьётся с той же статистикой у Winline/Fonbet/BetBoom. Часть такой статистики Betcity отдаёт «зависимыми» событиями (`is_dep=1`), где префикс попадает даже в имена команд («УГЛ Кайрат-Алматы») — такой префикс срезается у ОБЕИХ команд, иначе событие не сшивается ни с родительским, ни с другими БК. Двойной исход, точный счёт и турнирные пропы (аутрайты) пропускаются — они используют другую форму блока и не являются простым двухисходным рынком конкретного матча; комбинированные ставки («П1 и обе забьют») отсекаются строгим совпадением названия рынка, чтобы не склеиться в «вилку» с обычной «Обе забьют».
- **Полная роспись рынков Betcity** (`BETCITY_FULL_MARKETS=1`, по умолчанию включено): общий снимок линии несёт лишь ~3 рынка на событие (топ-линии), а вся роспись — лестницы тоталов и фор, азиатские линии, таймы/периоды, индивидуальные тоталы, «Обе забьют», чет/нечет — приходит ТЕМ ЖЕ эндпоинтом `d/off/events` с параметром `ext=1` и списком `id_ev` в теле. Роспись содержит ~160 рынков на событие (из них в двухисходные котировки разворачивается ~70: остальное — точный счёт, «время первого гола», комбинированные «П1 и ТБ 2.5» и прочее, что у разных БК означает разное и в вилки не сшивается). На живой линии это ~84 000 котировок вместо ~7 500. Гранулярный per-событийный путь `off/ext` при этом действительно закрыт файрволом (соединение рвётся даже из настоящего браузера с валидной cookie-сессией) — но он и не нужен. Ограничения сервера: больше ~250 id в одном запросе → 500, поэтому пачка — `BETCITY_EXT_BATCH` (≤200). Роспись есть примерно у 2200 из ~2900 событий линии (у остальных её просто нет — поле `cnt_ext_add` пустое) и весит ~9.5 КБ на событие в сжатом виде, т.е. ~20 МБ за полный обход. Качать это каждый цикл незачем, поэтому роспись обновляется **по кругу** — не чаще раза в `BETCITY_EXT_REFRESH` секунд на событие и не более `BETCITY_EXT_MAX_REQUESTS` запросов за цикл (пачки идут параллельно, `BETCITY_EXT_WORKERS`), с приоритетом самых «старых» событий и ближайших по времени старта; при дефолтах полный обход занимает ~2 цикла и ~10 МБ трафика на цикл. Роспись старше `BETCITY_EXT_MAX_AGE` выбрасывается — лучше меньше рынков, чем ставка по кэфу, которого уже нет. Betcity рвёт ощутимую долю соединений (на живой линии — до трети попыток: RST или ошибка TLS-рукопожатия), поэтому каждый запрос переигрывается до трёх раз с закрытием пула соединений перед повтором — иначе один обрыв стоил бы всей линии Betcity на цикл.
- Парсер **Melbet** работает через публичный JSON-фид линии (движок 1xBet, см. `app/parsers/melbet.py`) — без браузера и авторизации: `LineFeed/GetSportsShortZip` даёт список видов спорта, `LineFeed/GetChampsZip?sport=<id>` — чемпионаты вида спорта вместе со числом событий в каждом, `LineFeed/Get1x2_VZip?champs=<id>&count=50&mode=4` — события чемпионата с рынками, а `LineFeed/GetGameZip?id=<событие>&isSubGames=true` — полную роспись события: лестницы тоталов и фор целиком, индивидуальные тоталы, «обе забьют», плюс список подигр. Роспись качается пулом потоков (`MELBET_FULL_MARKETS_WORKERS`, выключается `MELBET_FULL_MARKETS=0`), лайв берётся тем же фидом по пути `LiveFeed`. База фида (домен + префикс `/service-api`) перебирается автоматически, как у Fonbet, и запоминается; задать вручную — `MELBET_API_HOST`. Неудачный перебор повторяется не чаще раза в 5 минут (каждая попытка — это таймаут на каждое зеркало), и пропущенный из-за этой паузы обход пишет в лог, сколько ещё ждать, — иначе «Melbet: 0 котировок» выглядел бы беспричинным. Когда фид отвечает **страницей вместо JSON**, парсер разбирается, что это за страница, потому что лечится это тремя разными способами: защиту от ботов (`DDoS-Guard`, `Cloudflare`, капча) проходит прогретая сессия — парсер заходит на сам сайт за куками и повторяет запрос; переадресация на другой домен означает переезд площадки, и новый домен тут же пробуется сверх списка зеркал; всё остальное — не тот префикс пути. На этот последний случай есть **поиск адреса по самому сайту**: если ни один известный адрес не сработал, парсер скачивает скрипты страницы и достаёт из них путь, по которому за линией ходит сама страница (в том числе когда он собирается в шаблонной строке `${host}/service-api/LineFeed/…`). Так переезд префикса чинится сам, без правки настроек на сервере. Посмотреть на всё это глазами — `venv/bin/python -m app.diagnose_melbet --api`: он печатает, что каждая площадка ответила именно вашему серверу, какие адреса нашлись в скриптах и какой из них отдал линию. Отдельно ловится зеркало, которое **проверку проходит, а линию не отдаёт**: проверка дёргает только справочник видов спорта, и площадка вполне может ответить на неё, закрыв для адреса сервера остальные эндпоинты. Раньше перебор каждый раз останавливался на таком зеркале, и Melbet молча сидела на нуле при живых остальных; теперь пустая прематч-линия (а её не бывает — в линии всегда тысячи событий) откладывает зеркало на полчаса, и следующий обход сразу идёт к другому.
- **Фид Melbet принимает только те строки запроса, которые шлёт сам сайт** — это главная его особенность, и на ней парсер один раз уже сломался целиком. Лишний параметр не игнорируется: в ответ приходит `406 NotAcceptable` на весь запрос. Проверено на живом фиде: `?sports=1&count=50&mode=4` — это 200, а `?count=50&mode=4&sports=1` — уже 406, то есть **значим даже порядок параметров** (фильтр идёт первым); `lng` ломает `Get1x2_VZip` и `GetChampsZip` при любом значении, `mode` и `getEmpty` — `GetSportsShortZip`; `count` обязан быть кратен пяти (`count=8` → 406); зато без `mode=4` фид отвечает 200 и ПУСТЫМ списком. Поэтому наборы параметров в парсере записаны ровно так, как их шлёт сайт, и **пересортировывать ключи в этих словарях нельзя**. Языка в запросах нет вовсе: фид и без него отвечает по-русски, а по русским названиям команд события и сшиваются с остальными БК РФ.
- **Линия Melbet собирается по чемпионатам.** Одним запросом фид отдаёт максимум 50 событий, сколько ни проси (`count=500` вернёт те же 50), поэтому запрос «весь вид спорта» — это лишь верхушка: 50 матчей из ~2700 по футболу. Обход идёт иначе: список видов спорта → чемпионаты каждого вида (~850 на всю линию) → события каждого чемпионата. Это ~900 запросов и ~7500 событий, то есть вся линия целиком; переключается на быстрый режим «только верхушка» через `MELBET_CHAMPS=0`. У чемпионатов, где событий больше 50 (бывает и сотня), остальные события добираются из индекса чемпионата (`GetChampZip`) — там их полный список, но без рынков, поэтому рынки к ним приезжают уже с росписью. Если фид оборвал часть запросов (под нагрузкой он это делает), линия добирается запросами по видам спорта, а в лог идёт сводка причин отказов — без неё неполная линия выглядела бы просто короткой.
- **Почему парсер Melbet не верит кодам рынков на слово.** В отличие от всех остальных БК, этот фид не подписывает рынок ни одним словом — у исхода только числа: `{"G": 17, "T": 9, "C": 1.85, "P": 2.5}` (группа рынка, код исхода, коэффициент, линия). Словарь кодов БК не публикует, а открытые разборы движка друг другу противоречат (в одном `T=10` — «тотал меньше», в другом — «тотал больше, альтернативная линия»). Ошибиться тут дорого: перепутав «больше» и «меньше», сканер сшил бы ТБ Melbet с ТМ другой БК и показал «вилку 15 %», на которую поставят деньги. Поэтому коды считаются **гипотезой, которую каждый обход проверяет по самой линии** (`app/parsers/melbet_layout.py`) — по тому, что верно у любой БК независимо от нумерации: лестница тоталов монотонна (чем выше линия, тем дороже «больше»), фора фаворита отрицательна (кто фаворит — известно из исхода 1X2 того же матча), индивидуальный тотал фаворита выше, «обе забьют» дешевеет с ростом результативности матча. Каждое событие даёт голос, решение принимается по всей линии сразу: голоса «против» победили — стороны переворачиваются с предупреждением в логе; голоса разделились пополам — значит в одну группу попали разные по смыслу рынки, и такое семейство рынков **не отдаётся вовсе**. По той же причине из нескольких групп с одинаковыми кодами (тотал матча, тотал тайма, азиатский тотал) берётся только одна — самая массовая в компактном снимке линии (а если семейства в снимке нет вовсе — как у «обе забьют», которую отдаёт только полная роспись, — самая массовая в росписи); рынки подигр берутся отдельно и получают период из названия подигры («1-й тайм» → `scope=half1`), а подигра без названия или с двумя разными наборами тоталов пропускается. Что именно приехало с сайта и к каким выводам пришла проверка, показывает `python -m app.diagnose_melbet` (таблица «группа + код исхода», счёт голосов, пример разобранного события); если по этой таблице видно, что выбрана не та группа, её можно закрепить руками — `MELBET_GROUPS=total=17,hcap=2`.
- Из Melbet берутся 1X2 и победитель без ничьей, лестницы тоталов и фор, индивидуальные тоталы обеих команд, «Обе забьют» и те же рынки у подигр. Подигра у этого фида — это не только тайм или период: у неё есть предмет счёта (`TG`: «Угловые», «Жёлтые карточки», «Удары в створ») и период (`PN`: «1-й тайм»), из них и собирается scope, поэтому «тотал угловых 1-го тайма» сшивается с таким же рынком других БК, а не с тоталом голов всего матча. Рынки подигры лежат за отдельным запросом — её собственным `GetGameZip`, — а подигр у одного футбольного матча бывает под три десятка, поэтому берётся только `MELBET_SUBGAMES` штук на событие, и периоды в этой очереди идут раньше предметных подигр.
- **«Обе забьют» у Melbet** — единственный её рынок без линии: две котировки около двойки, и монотонностью лестницы, как тотал, его не проверишь. Опора для него другая: этот рынок жёстко связан с результативностью матча (чем больше голов ждёт БК, тем чаще забивают обе команды), а сколько голов она ждёт — видно из её же тотала, по линии, где кэфы «больше» и «меньше» ближе всего друг к другу. Линия делится на низовые матчи (центр тотала ≤ 2.25) и результативные (≥ 3.25), и разметка принимается, только если **обе половины пришли к одному выводу**: в низовых «да» должно быть дороже «нет», в результативных — дешевле. Одной половины мало — так же вела бы себя, например, пара кодов «обе забьют в 1-м тайме», которая отличается только на результативных матчах. Разошлись половины, не набралось голосов в одной из них или не подтвердился сам тотал — рынок не отдаётся. Разгромные матчи (кэф фаворита ниже 1.25) в голосовании не участвуют: там все голы кладёт одна команда, и связь с общим тоталом ломается.
- Чет/нечет, двойной шанс и точный счёт из Melbet **намеренно не берутся**. Чет/нечет проверить нечем в принципе: у честной линии «чёт» и «нечет» почти равновероятны при любом тотале, никакой структурный признак не скажет, который из двух кодов какой, — а перепутав их, сканер сложил бы свой «чёт» с чужим «нечет» и показал бы вилку на пустом месте. Остальное либо не двухисходное, либо не сшивается с другими БК. Появится подтверждённый словарь имён рынков — добавим.
- **Ссылки на страницу матча** собираются в парсерах (`_event_url`) и у двух БК устроены неочевидно — обе успели поработать «в никуда». **Winline**: путь `/stavki/event/<id>`, который стоит в `href` карточек на самом сайте, при открытии ПО ССЫЛКЕ не работает — роутер не успевает достать событие и сбрасывает на главную; настоящий адрес состоит из четырёх сегментов, `/{stavki|live}/sport/<вид>/<страна>/<чемпионат>/<id>`, и с меньшим их числом маршрут снова не узнаётся. Слаги роутеру безразличны (адрес с `x/y/z` открывает ту же страницу), поэтому неизвестная страна ссылку не ломает; в лайв-кадре фида справочника стран нет, и страна берётся по чемпионату из прематча. **Melbet** сложнее, и тут два независимых подвоха. Первый — номер: в адресе стоит **постоянный номер события `CI`**, а не `I`, по которому парсер ходит за росписью. Второй — **у площадок движка разные пространства номеров и разные маршруты**: melbet.ru открывает матч внутренним маршрутом приложения (`/ru/sport/event-details/<чемпионат>-<событие>-<страна>-<спорт>-0-<лайв>-0-<команды>`), международные зеркала — SEO-адресом (`/ru/line/<вид>/<id чемпионата>-<чемпионат>/<CI>-<команды>`), и номера чемпионатов/событий у них **не совпадают**. Поэтому ссылка по умолчанию ведёт на ту площадку, **откуда пришла линия** (базу фида парсер выбирает перебором и может уйти на .com, когда melbet.ru не пускает адрес сервера) — иначе сайт просто не знает таких номеров и отдаёт 404 при любом формате. Явно заданный `MELBET_SITE_HOST` всегда важнее, формат пути переопределяется через `MELBET_EVENT_URL`, а подобрать его на живом сайте помогает `venv/bin/python -m app.diagnose_melbet --links`: он строит варианты на реальных событиях, дёргает каждый и показывает, какой открыл матч. Подигра ведёт на страницу родительского матча (своей у неё нет), а без номера события ссылка ведёт в раздел линии — открыть раздел лучше, чем выдуманный адрес с 404.
- Точность сопоставления: события сшиваются по нормализованной паре команд **и кластеру времени начала** — первый/ответный матчи и мужские/женские пары одних клубов не смешиваются; вилки с доходностью выше `ARB_MAX_PROFIT` (по умолчанию 25 %) отбрасываются как ошибки сопоставления. Перед сопоставлением разные написания имени одной команды между БК сливаются в каноническое (`build_name_canon_map`, см. пункт 8 выше) — иначе опечатка/транслитерация в имени у одной БК срывала бы склейку события целиком. Ключ рынка при этом приводится к общей форме (`canon_market_key`, см. пункт 5 выше): разойдись парсеры в записи пустого `scope` или в формате линии — и один и тот же рынок разъехался бы по разным группам, а вилка по нему не нашлась бы вовсе. Допуск времени старта (`_start_tolerance` в `app/arbitrage.py`) зависит от вида спорта:
  - `START_TS_TOLERANCE` (по умолчанию **60 мин**) — для всех обычных видов спорта. Диагностика (`app/diagnose_overlap.py`) на живых данных нашла десятки пар событий с ИДЕНТИЧНЫМИ (после нормализации) именами команд у разных БК, но start_ts различался на 35–180 мин — похоже на неточность/часовой сдвиг в фиде конкретной БК для зарубежных турниров (теннис-челленджеры, футбол малых лиг и т.п.), а не на разные матчи; одна и та же пара соперников не встречается повторно в течение пары часов в один день, поэтому допуск увеличен с прежних 30 мин.
  - `START_TS_TOLERANCE_RAPID` (по умолчанию 30 мин, старое строгое значение) — для «быстрых» турниров, где та же пара соперников может сыграть НЕСКОЛЬКО матчей за вечер с интервалом в минуты (виртуальный футбол типа «FC 26 ... 2x3 мин.», лиги-однодневки; распознаётся по шаблону `N x M мин` в названии турнира). Здесь расширять допуск ОПАСНО — можно склеить два разных матча одной пары в одну «вилку».
  - `START_TS_TOLERANCE_COMBAT` (по умолчанию 12 ч) — для **единоборств** (MMA/бокс): время боя на карде оценочное и у разных БК расходится на часы (bc.game 21:45 / BetBoom 23:00 для одного боя UFC), а одна пара бойцов не дерётся дважды за день, поэтому бой не разваливается на два «события».

## Админка, аккаунты БК и авто-ставки

⚠️ **Это самая рискованная часть проекта.** Авто-ставки могут привести к: банам/лимитам аккаунта у БК (букмекеры активно борются с «вилочниками»), финансовым потерям при сбое автоматизации (неверный кэф/сумма/исход), а в некоторых юрисдикциях — к нарушению правил БК или закона. Проверяйте законодательство своей юрисдикции и правила БК самостоятельно; используете на свой риск.

### Вход

- URL: `/admin`. Сама страница лежит за шлюзом сайта, так что вход двухступенчатый: сначала `/login` (реквизиты администратора там подходят), потом форма админки. Это не лишняя формальность: /admin не должен быть виден тому, кто не прошёл шлюз.
- Логин по умолчанию: `admin` / `admin1` — задаётся `ADMIN_USERNAME` / `ADMIN_PASSWORD`.
- Сессия — подписанный cookie-токен (HMAC на стандартной библиотеке, без JWT-зависимостей), живёт `ADMIN_SESSION_TTL` секунд (по умолчанию 12 часов).
- `SECRET_KEY` — секрет для подписи сессий и шифрования логинов/паролей аккаунтов БК в базе. Если не задан явно, генерируется один раз и сохраняется в файл `.secret_key` рядом с проектом (в `.gitignore`, не коммитьте его). На проде задайте `SECRET_KEY` явно переменной окружения — иначе после потери файла расшифровать сохранённые пароли БК не получится.

### Сканер: переключатель лайва

Раздел «Сканер» — единственная настройка админки, которая **сохраняется в базе** и переживает перезапуск (флаги авто-ставки, наоборот, сознательно только runtime — см. ниже).

Галочка «Лайв-сканер включён» + кнопка «Применить» гасят и поднимают лайв **на ходу**, без перезапуска сервера. Зачем это нужно: лайв обновляет свои БК каждые полторы секунды и делит с прематчем процессор и сеть, а Python выполняет байт-код одним потоком за раз (GIL) — на слабом VPS лайв ощутимо замедляет прематч. В замерах на живой линии выключение лайва подняло сбор BetBoom с ~9 000 до ~50 000 котировок: полному websocket-фиду линии хватает отведённых ему 90 секунд только тогда, когда процессор не занят лайвом.

Выключение не мгновенное: воркеры лайв-БК завершают начатые обходы (до полутора минут у BetBoom), поэтому строка состояния под галочкой показывает и желаемое состояние, и фактическое («Лайв останавливается — БК докачивают текущие обходы…»). Как только лайв остановлен, его котировки забываются — показывать кэфы режима, который больше не обновляется, нельзя: в лайве старый кэф опаснее его отсутствия. Значение при первом запуске задаётся переменной `LIVE_ENABLED`, дальше приоритет у сохранённого в админке.

### Парсеры БК: выключение и перезапуск

Раздел «Парсеры БК» — плитка на каждую БК: сколько котировок она принесла в прематче и в лайве, когда это было (или что обход идёт прямо сейчас), галочка «вкл/выкл» и кнопка «Перезапустить».

**Выключение БК.** У каждой БК свои беды: Betcity рвёт соединение с адресом, который слишком часто просит всю линию; Winline и BetBoom тянут многомегабайтные websocket-фиды и едят память; у зарубежной bc.game расходятся с БК РФ написания имён команд, из-за чего её «вилки» чаще оказываются ошибкой сопоставления. Раньше выключить одну БК можно было только переменной окружения и перезапуском сервера. Теперь выключенная БК:

- не опрашивается вообще — освободившиеся процессор и сеть достаются остальным;
- пропадает из вилок **сразу**, не дожидаясь конца начатого обхода (у Betcity он длится под минуту): её котировки забываются, а результат обхода, который шёл в момент выключения, отбрасывается. Иначе кэфы выключенной БК ещё минуту висели бы в вилках как живые, и было бы непонятно, сработала кнопка или нет;
- котировки именно **забываются**, а не доживают до `ODDS_TTL` — держать в вилках кэфы, которые никто не обновляет, нельзя, по ним не поставишь;
- остаётся выключенной после перезапуска сервера (флаг хранится в базе), а в шапке сайта её чип помечен как выключенный, чтобы «пропавшая» БК не выглядела сломанной.

Действует это почти сразу: воркер БК проверяет флаг на каждом витке цикла, а пауза между обходами прематча (минуты) для этого прерывается — иначе решение оператора применялось бы через полчаса.

**Перезапуск.** Кнопка «Перезапустить» пересоздаёт парсер БК: новая сессия `requests`, новые cookie, чистое websocket-состояние, котировки с нуля. Помогает в неприятном случае «БК отвечает, но линия не обновляется» — раньше это лечилось только перезапуском всего процесса. Рядом, в разделе «Сканер», есть перезапуск сканера целиком (прематч и/или лайв — все БК получают чистые сессии) и **перезапуск сервера**: процесс поднимается заново теми же аргументами (`os.execv`), что нужно после смены переменных окружения или `git pull` на VPS. На несколько секунд сайт при этом недоступен.

### Игроки: учётные записи для входа

Сканер стоит на VPS с публичным адресом, и раньше его видел любой, кто знает IP. Пароль на входе это закрывал, но один общий пароль на всех не отвечает на вопрос, **кто именно** пришёл, — а без этого не завести ни личный баланс, ни журнал прибыли. Поэтому вход на сайт устроен как учётные записи (`app/players.py`, таблица `players`), и раздел админки **«Игроки»** — единственное место, где они появляются:

- **Регистрации нет.** Учётку заводит администратор: логин, пароль и (по желанию) отображаемое имя со стартовым балансом. Реквизиты он передаёт человеку сам.
- **Пароль не показывается никому**, включая самого администратора: в базе лежит только хэш (PBKDF2-HMAC-SHA256, 200 000 итераций, случайная соль). Забытый пароль не восстанавливается, а **задаётся заново** кнопкой «Пароль» в строке игрока.
- **Логин не различает регистр** и хранится в нижнем регистре: его диктуют голосом и пересылают в мессенджере, и «Petya» вместо «petya» — не повод не пустить человека на сайт. Пробелы по краям срезаются по той же причине. Разрешены буквы (в том числе русские), цифры, точка, дефис и подчёркивание, длина 3–32 символа; пароль — от 6 символов.
- **Выключенная учётка** (галочка «Вкл») теряет доступ **немедленно**, а не когда истечёт срок её сессии: учётка перечитывается из базы на каждый запрос. Журнал ставок и баланс при этом остаются на месте — это способ временно закрыть доступ, ничего не потеряв. Удаление, наоборот, уносит журнал вместе с игроком.
- В таблице видно деньги каждого: стартовый баланс, прибыль по журналу, текущий баланс, число сохранённых ставок и когда он заходил последний раз.

Сессия игрока — отдельная подписанная cookie `player_session`, живёт `SITE_SESSION_TTL` (по умолчанию 30 суток). Сессия админки и сессия по общему паролю остались собственными cookie и работают независимо.

Без входа доступны только страница `/login`, её стили со скриптом и ручки `/api/access/*`; всё остальное, включая `/admin` и `/api/*`, закрыто.

**Защита от перебора.** Не больше `SITE_LOGIN_MAX_FAILS` неудачных попыток с одного IP за `SITE_LOGIN_FAIL_WINDOW` секунд (по умолчанию 10 за 5 минут). Счётчики живут в памяти процесса: перебор идёт минутами, и переживать перезапуск им незачем. Ошибка входа одна на все случаи («Неверный логин или пароль») — подсказывать, что логин существует, а не подошёл пароль, значит помогать перебору.

### Профиль игрока: стартовый баланс и журнал ставок

Страница `/profile` (ссылка с балансом — в шапке сайта). Ставки игрок делает руками на сайтах БК, и сканер о них ничего не знает; чтобы считать прибыль, он нажимает в карточке вилки **«💾 Сохранить ставку»**:

- вилка со всеми плечами (исход, кэф, БК, сумма), рынком и матчем ложится в его личный журнал;
- баланс растёт на **гарантированную прибыль** этой вилки — выигрыш при любом исходе минус сумма всех плеч;
- суммы берутся те же, что человек видит в модалке (он мог округлить плечи по-своему), но арифметика перепроверяется на сервере: прибыль, которую прислал браузер, не принимается на веру.

**Баланс нигде не хранится отдельным числом.** Он всегда считается как «стартовый баланс + прибыль всех сохранённых ставок»: иначе удаление ошибочной записи оставляло бы его завышенным навсегда. Стартовый баланс (деньги, с которыми игрок зашёл на дистанцию — сумма по всем счетам БК) он задаёт себе сам в настройках профиля, там же меняет отображаемое имя и собственный пароль.

В журнале видно, когда сохранена запись, матч, рынок, все плечи, сумму, выигрыш и прибыль. Крестик удаляет ошибочную запись — баланс пересчитывается сам. Чужие записи недоступны: `id` ставки приходит из браузера, поэтому удаление и чтение всегда ограничены `player_id` текущей сессии.

Администратор видит те же деньги в разделе «Игроки», а разобрать спорную запись может через `GET /api/admin/players/{id}/bets`.

Вошедшие **администратором или по общему паролю** профиля не имеют: кнопки «Сохранить ставку» им не показывают, а `/profile` объясняет, почему журнала нет. Личный баланс — свойство учётки игрока, и приписывать ставки безымянному входу некуда.

### Доступ к сайту: ограничения по IP и запасной пароль

Раздел админки **«Доступ к сайту»** (шлюз-middleware в `app/main.py`, логика — в `app/access.py`) отвечает уже не за то, закрыт ли сайт — закрыт он всегда, — а за то, откуда и чем ещё в него можно войти:

- **Общий запасной пароль.** Остался с тех пор, когда сайт закрывался одним паролем на всех: он пускает на сайт **без учётки**, но профиля и журнала ставок у такого посетителя не будет. Задаётся здесь же (хранится хэшем) или переменной `SITE_PASSWORD`; заданный в админке важнее. Кнопка «Снять пароль» убирает только его — учётки игроков и вход администратора работают независимо. Реквизиты администратора тоже открывают сайт: держать в голове лишний пароль незачем, а права админки заведомо шире.
- **Белый список IP и подсетей.** Сам по себе **больше никого не пускает**: раз у каждого игрока своя учётка со своим журналом, «свой адрес» не отвечает на вопрос, кто именно пришёл. Список нужен строгому режиму. Кнопка «+ Мой адрес» подставляет адрес, с которого вы сейчас смотрите админку.
- **Строгий режим.** Пускать ТОЛЬКО адреса из списка — вариант «сайт вижу только я со своего адреса»; логин при этом спрашивается всё равно, так что украденная cookie с чужого адреса не сработает. Включить его, пока в списке нет вашего собственного адреса, приложение не даст: иначе вы заперли бы себя снаружи (то же касается пустого списка).
- **Чёрный список.** Не пускает конкретные адреса всегда, раньше всех прочих проверок. Действующая сессия админки его обходит — запереть себя оператор не должен.

⚠️ **Про обратный прокси.** За nginx адрес соединения — всегда `127.0.0.1`, настоящий IP приходит заголовком `X-Forwarded-For`. Заголовку можно верить только тогда, когда запрос пришёл из локальной сети, то есть от своего же nginx: иначе посетитель, ткнувшись в uvicorn напрямую (порт 8000 открыт наружу), подобрал бы себе адрес из белого списка одним заголовком. Приложение так и делает и берёт **последний** адрес цепочки — тот, который добавил сам nginx. Если проксирования нет, поставьте `SITE_TRUST_PROXY=0`, а порт uvicorn в любом случае лучше закрыть файрволом (шаг 7).

⚠️ Это защита «от посторонних глаз», а не сейф: без HTTPS (шаг 8) пароль идёт по сети открытым текстом.

### Кто на сайте: устройства посетителей и бан по устройству

Раздел админки **«Кто на сайте»** отвечает на вопрос, которого не было в логах: кто прямо сейчас смотрит вилки. В логах uvicorn виден только IP, а с телефона он меняется каждый день — по нему не отличить нового человека от своей же второй вкладки. Поэтому каждому браузеру выдаётся cookie с меткой **устройства** (`app/visitors.py`), и в таблице видно:

- **устройство** — браузер, ОС и тип (телефон, планшет, компьютер, робот), разобранные из `User-Agent`;
- **адрес** — последний, а в подсказке — все, с которых это устройство приходило (у телефона их накапливается несколько);
- **активность** — «сейчас на сайте» (запрос за последние `VISITOR_ONLINE_WINDOW` секунд) или сколько времени назад заходило, число запросов и когда устройство появилось впервые;
- пометки: `это вы`, `админка` (устройство заходило в админку), `вошёл` (есть действующая сессия — учётка игрока или общий пароль), `забанен`.

**Бан.** Кнопка «Забанить» закрывает сайт для устройства целиком — и страницы, и API (`/api/*` отвечает 403). «Забанить с IP» дополнительно кладёт его текущий адрес в чёрный список: адрес блокирует всех, кто за ним сидит, зато устройство, сменившее браузер, уже не пройдёт. Чёрный список действует **всегда**, даже когда сайт в остальном открыт: выгнать одного посетителя нужно уметь, не закрывая сайт паролем от всех. Правится он и кнопкой в списке устройств, и руками в разделе «Доступ к сайту».

Cookie чистится в два клика, поэтому бан устройства запоминает ещё и **отпечаток браузера** (`User-Agent`, язык, платформа): если с того же адреса приходит тот же самый браузер, но уже без cookie — он блокируется автоматически и появляется в списке с пометкой «забанен (вернулся)». Совпасть должны И отпечаток, И адрес: одного отпечатка мало (у двух одинаковых телефонов он общий, и бан цеплял бы посторонних), одного адреса — тоже (за домашним роутером сидит вся семья). Разбан оригинала снимает и такие автоматические баны.

Запереть себя нельзя, это проверяется в трёх местах: своё текущее устройство забанить не даёт API, свой адрес не даёт положить в чёрный список ни кнопка «Забанить с IP», ни поле в разделе «Доступ к сайту», а действующая сессия админки обходит любой бан — вход в `/admin` остаётся открытым, даже если вы заблокировали адрес, с которого сидите.

⚠️ Бан по устройству — это «выставить за дверь», а не сейф: настойчивый гость сменит браузер и сеть и придёт как новое устройство. Настоящая защита — учётные записи (раздел выше) и строгий режим белого списка; бан удобен, когда надоел конкретный посетитель или робот. Если это игрок — надёжнее снять галочку «Вкл» с его учётки: доступ пропадёт сразу и с любого устройства.

Список живёт в памяти и сбрасывается в базу раз в `VISITORS_FLUSH_INTERVAL` секунд: каждая открытая вкладка опрашивает сервер раз в 5 секунд, и писать это в SQLite на каждый запрос — впустую тратить процессор, который нужен обходам БК. Сам бан, наоборот, пишется в базу сразу же и переживает перезапуск. Устройств хранится не больше `VISITORS_MAX` (забаненные — сверх этого числа и не вымываются никогда, иначе бан тихо снимался бы сам). Кнопка «Забыть» убирает устройство из списка вместе с баном — при следующем заходе оно появится заново. Весь учёт выключается переменной `VISITORS_ENABLED=0`: тогда cookie не выдаётся и список пуст.

### Аккаунты БК: баланс и лимит ставки на вилку

В админке можно добавить аккаунт (логин/пароль) для каждой из 6 БК: Winline, Melbet, BetBoom, Fonbet, Лига Ставок, bc.game. Логин/пароль хранятся в базе **только в зашифрованном виде** (Fernet, ключ производный от `SECRET_KEY`) — по API отдаётся замаскированный логин, пароль никогда не отдаётся.

- После добавления (или по кнопке «Обновить баланс») сканер пытается получить баланс через отдельный headless-браузер (не общий с браузером сканера линии — сессии аккаунтов разных БК не должны пересекаться). Фон обновляет баланс каждые `BALANCE_REFRESH_INTERVAL` секунд (по умолчанию 5 минут).
- Пока баланс аккаунта неизвестен (ещё не обновлялся или обновление упало с ошибкой) — в выдаче вилок (`GET /api/arbs`, `/api/live/arbs`, поле `max_stake` у каждой вилки) лимит будет `null`: система осознанно **не показывает придуманный лимит там, где баланс не подтверждён**.
- Когда баланс известен, `max_stake` вилки — минимум из лимитов по каждой её ноге: `min(баланс аккаунта БК × AUTOBET_MAX_BALANCE_FRACTION, AUTOBET_MAX_STAKE)`.

### Способ входа: по телефону или по логину

В российскую БК входят либо номером телефона, либо логином, и это **не одно и то же поле**: у Winline и Melbet форма разведена на две вкладки, у каждой свой `input`. Поэтому при добавлении аккаунта админка спрашивает способ входа, а не пытается его угадать — угадать его нельзя в принципе: номер клубной карты Melbet тоже состоит из одних цифр, и от телефона его не отличить.

Выбирайте тот способ, **которым вы сами входите в этот кабинет руками**. От него зависит:

- какую вкладку формы нажмёт коннектор (`Телефон` против `Логин`);
- в какое поле впишет реквизит;
- отрежет ли у номера код страны. Телефон можно писать как угодно (`+7 (999) 123-45-67`, `89991234567`, `9991234567`) — в поле уйдут 10 цифр без кода: у БК префикс `+7` стоит отдельным элементом рядом с полем, и полный номер маска сдвинет, отправив в БК чужой.

Способ хранится вместе с аккаунтом (столбец `login_type`) и **не шифруется**: это не секрет, а настройка формы. Менять его можно в таблице аккаунтов — после смены баланс перечитывается заново, как после смены пароля. Аккаунтам, заведённым до появления выбора, достаётся «по телефону»: именно так они и вводились.

Список способов фронтенд берёт с сервера (`GET /api/admin/bookmakers` → `login_types`), а не хардкодит: у **bc.game** входа по российскому номеру нет вовсе (там e-mail или никнейм), и предлагать там телефон — обречь оператора разбираться, почему форма молча не отправляется. Способ, которого БК не принимает, API отвергает с `400`.

### Проверка аккаунта из командной строки

Для ручной проверки аккаунтов без похода в UI есть диагностический скрипт — данные берутся **только из переменных окружения** (никогда из аргументов командной строки, чтобы не осели в истории shell). Один аккаунт:

```bash
TEST_BOOKMAKER=Winline TEST_BK_LOGIN=... TEST_BK_PASSWORD=... \
TEST_BK_LOGIN_TYPE=phone python3 -m app.diagnose_account
```

Несколько аккаунтов сразу (по набору переменных `<БК>_TEST_LOGIN`/`<БК>_TEST_PASSWORD`/`<БК>_TEST_LOGIN_TYPE` на каждую БК — префикс см. в докстринге `app/diagnose_account.py`):

```bash
WINLINE_TEST_LOGIN=... WINLINE_TEST_PASSWORD=... WINLINE_TEST_LOGIN_TYPE=phone \
MELBET_TEST_LOGIN=... MELBET_TEST_PASSWORD=... MELBET_TEST_LOGIN_TYPE=login \
FONBET_TEST_LOGIN=... FONBET_TEST_PASSWORD=... \
python3 -m app.diagnose_account
```

`<БК>_TEST_LOGIN_TYPE` — `phone` или `login`, не задан — способ по умолчанию для этой БК. Задавайте все эти переменные через секреты окружения (на своём сервере — `.env`/systemd, в Cursor Cloud Agent — Dashboard → Cloud Agents → Secrets), не через аргументы или чат.

**Разведка формы входа** — `--form <БК>`, пароля не требует вообще:

```bash
python3 -m app.diagnose_account --form Melbet
```

Скрипт открывает форму входа и печатает, что в ней реально лежит — вкладки, поля, кнопки, — а затем говорит, сходятся ли с этим настроенные селекторы: по каждому способу входа отдельно (`вкладка «Логин»: нажата`, `селектор поля 'input[name=…]': НИЧЕГО НЕ НАХОДИТ`). Не сошлось — он же печатает имена переменных окружения, которыми это правится **без правки кода** (`MELBET_TAB_LOGIN`, `MELBET_USERNAME_PHONE_SELECTOR`, …). Нужно это там, где форму невозможно увидеть из среды разработки — см. Melbet ниже.

Отдельно скрипт распознаёт случай, когда БК вообще не пустила на сайт (`Пожалуйста, отключите VPN` у Melbet, `Forbidden` у Fonbet), и говорит об этом прямо: полей на странице-заглушке нет и быть не может, чинить надо не селекторы, а адрес, с которого вы ходите.

### Что из этого реально проверено

⚠️ **Чтение баланса через браузер — экспериментальная, НЕ проверенная целиком на живых аккаунтах функция.** Статус на 2026-07-30 (проверено браузером из облачной песочницы — подробности и точные селекторы в докстринге `app/connectors/selenium_generic.py`):

- **Winline** — сценарий входа пройден целиком до проверки реквизитов, **обоими способами**. Модалка, обе вкладки, оба поля (`auth-phone-base` / `auth-username`), пароль и кнопка отправки подтверждены на живом сайте; капчи на форме нет. Кнопка входа приходит с атрибутом `disabled` и включается, только когда фронтенд принял оба поля — коннектор её дожидается (клик по отключённой кнопке Selenium выполняет молча, и форма просто не отправляется). Отправка заведомо неверных реквизитов доходит до ответа БК («Неверный телефон или пароль» / «Неверный логин или пароль»). Не проверено: сам успешный вход (не было тестового пароля), возможный СМС-код после него и селектор баланса.
- **Melbet** — движок 1xBet, вход тоже двумя способами (телефон и «ID/номер счёта»). **Селекторы не проверены и из этой песочницы проверены быть не могут**: `melbet.ru` отдаёт «отключите VPN» адресам дата-центров, а международные зеркала — страницу `/ru/block` на всё, кроме фида линии. Это то же ограничение, из-за которого линия Melbet требует российского IP (см. предупреждение в начале README и `venv/bin/python -m app.diagnose_melbet`), только сайту его недостаточно даже там, где фида хватает. Поэтому селекторы заданы намеренно широко, а уточняются на боевом сервере разведкой формы (`--form Melbet`) и переменными окружения.
- **BetBoom** — форма входа открывается, поля логина/пароля найдены, но отправка формы заблокирована **Google reCAPTCHA**. Автоматически её не проходим (умышленно) — коннектор поднимает явную ошибку вместо тихого зависания.
- **Fonbet** — `fonbet.ru`/`fon.bet` отдают анти-бот-заглушку «Forbidden» (ServicePipe) на любой запрос с датацентрового IP, даже в headed-режиме, ДО формы входа. Это не селекторы — нужен резидентный/мобильный российский IP, как и для Лиги Ставок (`LIGASTAVOK_PROXY`); поддержана аналогичная переменная `FONBET_PROXY` (и по аналогии `<БК>_PROXY` для остальных БК) — используется ТОЛЬКО отдельным браузером аккаунта, не общим браузером сканера.
- **Liga Stavok**, **bc.game** — не проверялись, селекторы — типовые заготовки.

Ни для одной БК не было успешного end-to-end чтения баланса живым логином, поэтому селектор баланса не подтверждён нигде.

Если обновление баланса падает с ошибкой — сначала проверьте, это селектор, не тот способ входа или один из блокеров выше: текст ошибки указывает на конкретную причину (капча, анти-бот, не найдена форма, «кнопка входа осталась заблокированной» — это как раз обычно перепутанные телефон и логин). Что реально лежит в форме, покажет `--form <БК>`. Переопределяются без правки кода:

| Переменная | Что задаёт |
|---|---|
| `<БК>_TAB_PHONE`, `<БК>_TAB_LOGIN` | видимые надписи вкладок способа входа |
| `<БК>_USERNAME_PHONE_SELECTOR`, `<БК>_USERNAME_LOGIN_SELECTOR` | поля имени пользователя на этих вкладках |
| `<БК>_USERNAME_SELECTOR` | общее поле, если вкладок у БК нет |
| `<БК>_PASSWORD_SELECTOR`, `<БК>_SUBMIT_SELECTOR` | пароль и кнопка отправки |
| `<БК>_LOGIN_BUTTON_TEXT` | надпись кнопки в шапке, открывающей модалку входа |
| `<БК>_BALANCE_SELECTOR` | элемент с балансом после входа |
| `<БК>_PROXY` | резидентный/мобильный прокси для входа именно в эту БК |

Префикс `<БК>` — имя БК заглавными без пробелов и точек: `WINLINE`, `MELBET`, `BETBOOM`, `FONBET`, `LIGA_STAVOK`, `BCGAME`. В любом случае проверяйте на тестовом аккаунте, прежде чем доверять авто-лимитам.

### Вход по cookie (альтернатива автологину)

И капча (BetBoom), и анти-бот-блок IP (Fonbet) относятся только к самому моменту входа — если сессия уже авторизована, дальше сайт её просто узнаёт по cookie. Это можно использовать: залогиньтесь в личный кабинет БК вручную, в **своём** обычном браузере (пройдя капчу/СМС-код как человек), затем скопируйте cookie этой сессии и передайте её коннектору — он подставит её в headless-браузер вместо сценария логина.

Как скопировать cookie: DevTools (F12) → вкладка Network → откройте/обновите личный кабинет БК → кликните на любой XHR/fetch-запрос к сайту БК → Headers → Request Headers → скопируйте значение заголовка `Cookie` целиком (это одна строка вида `name1=value1; name2=value2; …`).

Куда её вставить:

- **В админке** — при добавлении аккаунта есть необязательное поле «Cookie»; у уже добавленного аккаунта — кнопка «🍪 Cookie» в таблице (можно вставить/обновить/очистить пустым значением).
- **В диагностическом скрипте** — переменная `TEST_BK_COOKIES` (схема с одним аккаунтом) или `<БК>_TEST_COOKIES` (схема с несколькими), см. докстринг `app/diagnose_account.py`.
- **Напрямую в коде** — `<БК>_COOKIES` не читается автоматически из окружения для аккаунтов из БД (там cookie хранится зашифрованной в самой БД, как и пароль) — только для diagnose_account.py и напрямую через `get_connector(..., cookies=...)`.

Коннектор сам проверяет, похоже ли, что cookie дала вход (у Winline/BetBoom — по тому, исчезла ли кнопка «Войти»/«Вход» после подстановки cookie): если нет — откатывается на обычный сценарий логина (с той же капчей/анти-ботом, что и раньше). Cookie рано или поздно протухнет (сайт разлогинит сессию) — тогда просто повторите копирование из браузера. Учитывайте: некоторые БК могут привязывать сессию к IP/фингерпринту устройства — cookie, снятая с домашнего компьютера, не гарантированно будет работать при подстановке с IP сервера.

⚠️ **BetBoom — особый случай.** У него сессия — не браузерная cookie, а JWT-токен, обычно лежащий в `window.localStorage` (а не в заголовке `Cookie`). Для него в то же поле/переменную можно добавить запись `ls:key=value` (например `ls:token=eyJ...`) вместо/вместе с обычными cookie — имя ключа смотрите в DevTools → Application → Local Storage у своего аккаунта. Дополнительно подтверждено: BetBoom защищён Qrator с активной JS-фингерпринт-проверкой при каждой загрузке страницы, и запрос `POST /api/auth/check-token` с токеном, отправленным с ДРУГОГО IP, чем тот, где он был получен, возвращает `{"isNeedLogout": true}` — то есть сайт считает такую сессию недействительной. Поэтому одного токена может быть недостаточно — вероятно, дополнительно понадобится `BETBOOM_PROXY` с резидентным/мобильным российским IP того же региона, где вы вошли.

**Важно про безопасность:** никогда не присылайте сам cookie/токен (значение) в чат/переписку — только имя ключа для `ls:`. Реальное значение вставляйте либо прямо в админку (поле «Cookie», хранится зашифрованным), либо как переменную окружения/секрет.

### Авто-ставка на вилку

⚠️ **Сейчас авто-ставка спрятана из интерфейса** (`AUTOBET_UI=0`, значение по умолчанию): кнопки в карточке вилки нет, разделов «Авто-ставки» и «Журнал ставок» в админке нет. Спрятана, а не удалена — ручка `POST /api/autobet/place`, коннекторы, расчёт сумм и журнал остались на месте, и `AUTOBET_UI=1` возвращает всё как было. Ставки сейчас делаются руками, а кнопка «поставить за меня» рядом с реальными деньгами — лишний повод нажать не туда. Ниже описано, как это работает, когда интерфейс включён.

В окне «Поставить» у **лайв**-вилок (вкладки «Лайв-вилки» и «Лайв 1X2») есть кнопка **«⚡ Авто-ставка (лайв)»**. По клику сервер:

1. считает сумму ставки на каждую ногу вилки **по актуальным на момент клика кэфам и лимиту** — сумма НЕ приходит от браузера, туда передаётся только `match_key`;
2. если для какой-то ноги нет подключённого аккаунта с известным балансом — по этой ноге ставка не делается (явная ошибка вместо угадывания суммы);
3. размещает (или имитирует, см. ниже) ставку через коннектор нужной БК и пишет итог в журнал (виден в админке и через `GET /api/admin/bet_log`).

Управляется двумя флагами в разделе «Авто-ставки» админки (API — `GET`/`POST /api/admin/settings`):

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `AUTOBET_ENABLED` | `0` (выкл) | Разрешить кнопку авто-ставки вообще. Выключено — сервер отвечает `403` |
| `AUTOBET_DRY_RUN` | `1` (вкл) | Режим имитации: считает суммы и «жмёт кнопки» в коде, но **реального запроса на сайт БК не отправляет**. Настоящие ставки — только когда `AUTOBET_ENABLED=1` И `AUTOBET_DRY_RUN=0` одновременно |

Настройки, изменённые в админке, **не персистентны** — сбрасываются на значения из переменных окружения при перезапуске процесса: дополнительная защита от случайного включения реальных ставок после рестарта сервера.

⚠️ **Реальное размещение ставки (`place_bet`) не реализовано ни для одной БК.** DOM ставочного слипа (купона) у каждой БК свой, часто с доп. подтверждением или капчей, и без живого залогиненного аккаунта его невозможно ни увидеть, ни протестировать — вместо фейковых «рабочих» селекторов, которые тихо промахнутся мимо нужного исхода или суммы, `place_bet` в реальном режиме честно возвращает ошибку с прямой ссылкой на матч у БК («поставьте вручную»). При этом кнопка работает **полностью** в режиме имитации: весь конвейер (расчёт лимитов, распределение ставки между ногами, журнал, отображение результата в интерфейсе) можно проверить прямо сейчас, без единого реального запроса. Чтобы включить реальное размещение для конкретной БК — реализуйте `place_bet` в подклассе `SeleniumGenericConnector` (`app/connectors/selenium_generic.py`), после того как вручную изучите её ставочный слип на тестовом аккаунте.

### Код подтверждения (СМС/пуш) при входе

Некоторые БК запрашивают код при входе с нового устройства/IP (типично для VPS/дата-центра). Полностью убрать этот шаг нельзя — это защита самой БК, но код можно передать от человека боту:

1. Коннектор (в фоновом потоке) заходит на сайт и вводит логин/пароль; если сайт показал поле кода — коннектор блокируется и ждёт код (`app/otp.py::request_otp`).
2. Админка каждые несколько секунд опрашивает `GET /api/admin/otp_pending` и, если какой-то аккаунт ждёт код, показывает диалог для его ввода.
3. Введённый код уходит через `POST /api/admin/accounts/{id}/otp` — коннектор получает его и вписывает в форму на сайте.

⚠️ Как и остальная автоматизация входа, детект поля кода (`OTP_SELECTORS` в `app/connectors/selenium_generic.py`) — эвристика, не проверенная на живом запросе СМС ни у одной БК. Коды не переживают перезапуск сервера (ожидание просто истечёт по таймауту, попытка входа прервётся с понятной ошибкой).

### Ограничения безопасности авто-ставки

- `AUTOBET_MAX_BALANCE_FRACTION` (по умолчанию `0.9`) — не более 90 % баланса аккаунта на одну ставку.
- `AUTOBET_MAX_STAKE` (по умолчанию `5000` ₽) — жёсткий потолок одной ставки независимо от баланса.
- Каждая попытка (успешная и неуспешная, имитация и реальная) пишется в журнал с полным списком ног, сумм, кэфов и сообщений — доступен в админке («Журнал ставок») и через `GET /api/admin/bet_log`.

## API

| Метод | Описание |
|---|---|
| `GET /api/arbs?min_profit=2` | Текущие прематч-вилки с доходностью ≥ 2 % (`arbs` — двухисходные, `arbs_1x2` — «Исход 1X2»; у каждой вилки поле `max_stake` — лимит по балансу подключённых аккаунтов, `null` если баланс неизвестен) |
| `GET /api/live/arbs?min_profit=2` | То же для лайва, плюс `autobet_enabled`/`autobet_dry_run` |
| `GET /api/odds` | Все собранные прематч-матчи и котировки (по всем БК) |
| `GET /api/matches` | Все прематч-события, сгруппированные по матчу (дата, БК, число рынков) |
| `GET /api/live/matches` | То же для лайва |
| `GET /api/match?id=…` | Полная роспись одного матча: все рынки всех БК бок о бок |
| `GET /api/history?limit=100` | История найденных двухисходных вилок из SQLite |
| `GET /api/history_1x2?limit=100` | История найденных вилок «Исход 1X2» из SQLite |
| `POST /api/autobet/place` | Ставит (или имитирует) вилку по `match_key`/`kind3`/`live`. Требует вход в админку, см. раздел выше |
| `POST /api/access/login`, `/logout`, `GET /state` | Вход на сайт по логину и паролю (единственные ручки, открытые без входа) |
| `GET /api/profile/me` | Кто вошёл и сколько у него денег (`null`, если вошли не игроком) |
| `POST /api/profile` | Игрок правит свой профиль: имя, стартовый баланс, пароль |
| `GET /api/profile/bets?limit=200` | Журнал сохранённых ставок игрока |
| `POST /api/profile/bets` | Сохранить поставленную вилку (плечи с кэфами и суммами; прибыль пересчитывается на сервере) |
| `DELETE /api/profile/bets/{id}` | Удалить свою запись — баланс пересчитается |
| `POST /api/admin/login`, `/logout`, `GET /me` | Вход/выход/проверка сессии админки |
| `GET/POST /api/admin/players` | Учётные записи игроков с их деньгами; создание новой |
| `PUT/DELETE /api/admin/players/{id}` | Изменить (имя, баланс, вкл/выкл, новый пароль) или удалить игрока вместе с журналом |
| `GET /api/admin/players/{id}/bets` | Журнал ставок одного игрока |
| `GET /api/admin/bookmakers` | БК, к которым можно привязать аккаунт, и чем в каждую входят (`login_types`) |
| `GET/POST/PUT/DELETE /api/admin/accounts[/…]` | CRUD аккаунтов БК (в т.ч. `login_type`) + `POST .../refresh_balance` |
| `GET /api/admin/limits` | Текущие балансы и лимиты по каждой подключённой БК |

## Дисклеймер

Проект предназначен для образовательных целей. Букмекеры активно ограничивают/банят счета «вилочников» (в т.ч. с конфискацией средств по своим правилам); проверяйте законодательство вашей юрисдикции и правила БК.

Функция авто-ставок (раздел [«Админка, аккаунты БК и авто-ставки»](#админка-аккаунты-бк-и-авто-ставки)) добавляет дополнительные риски: хранение логинов/паролей от реальных денежных счетов (даже зашифрованных) и автоматизацию, которая может ошибиться в исходе, сумме или кэфе. По умолчанию всё выключено (`AUTOBET_ENABLED=0`) и работает в режиме имитации без единого реального запроса к БК (`AUTOBET_DRY_RUN=1`); реальная постановка ставки не реализована ни для одной БК (см. предупреждения в `app/connectors/selenium_generic.py`) — включайте на свой риск и только после того, как самостоятельно проверили и адаптировали автоматизацию для конкретной БК на тестовом аккаунте.
